## 零、 模块定位与分层缓存拓扑 (Module Positioning & Topology)

系统 3 位于 Master Pipeline 的入站第一道路由分支前（系统 1 协议归一化之后，系统 2 智能路由之前）：
* **成本阻断门禁**：对高频重复意图，通过 L1~L3 递进式缓存实现 **$15\text{ms}$ 极速响应并达成 \$0 算力支出**；
* **租户硬隔离安全**：强制将 `tenant_id` 与权限标签注入向量检索语句，**跨租户越权漏召回率严格为 0%**；
* **防否定句漂移**：引入轻量级 Cross-Encoder 语义二阶复核与命名实体（NER）比对，杜绝“支持”与“不支持”混淆；
* **Prompt 物理对齐**：标准化系统提示词与工具定义前缀，激发云厂商底层 Prompt Caching 复用，压降 60%~80% 成本；
* **双时钟无锁记账**：基于 LMAX Disruptor 异步将 Token 流水刷入 ClickHouse，并在租户超额时毫秒级熔断。

## 一、 L1~L3 递进式缓存查询与回填全链路时序图 (Cache Sequence Flow)

```mermaid
sequenceDiagram
    autonumber
    participant Req as 客户端标准请求
    participant L1 as L1 本地精确缓存 (Caffeine W-TinyLFU)
    participant L2 as L2 分布式向量缓存 (Redis 7.x HNSW)
    participant L3 as L3 交叉编码器 (Cross-Encoder & NER)
    participant Upstream as 上游大模型集群 (通过系统 2/4)
    participant Ring as LMAX Disruptor 异步事件环

    Req->>L1: 1. 计算 SHA-256(tenant_id + prompt)，查询本地内存
    alt L1 命中文本
        L1-->>Req: 极速返回 (耗时 <= 0.1ms, 标记 HIT-L1-EXACT)
    else L1 未命中 (穿透到 L2)
        Req->>L2: 2. 携带 tenant_id 过滤条件执行 HNSW 向量搜索 (Cosine >= 0.95)
        alt L2 向量相似度未达标 (< 0.95)
            L2-->>Upstream: 判定未命中 (Cache Miss, 耗时 <= 1.2ms)，透传上游推理
        else L2 向量初筛命中 (相似度 >= 0.95)
            L2->>L3: 3. 提交至 L3 执行语义反漂移与实体一致性复核
            L3->>L3: 检查否定句极性 (Polarity) 与电商核心实体 (SKU, 国家, 币种)
            alt L3 复核发现语义漂移 (如否定词冲突)
                L3-->>Upstream: 强制标记为失效，穿透给上游大模型
            else L3 复核完全一致
                L3-->>Req: 组装响应返回 (耗时 <= 15ms, 标记 HIT-L3-SEMANTIC)
                L3->>L1: 回填至 L1 本地缓存
            end
        end
    end

    opt 缓存未命中且上游成功返回 (异步回填与记账)
        Upstream-->>Req: 正常流式吐字完毕
        Upstream-)Ring: 异步发布 CacheIngestEvent & TokenBillingEvent
        Ring-)L2: 异步写入向量与租户元数据 (带 TTL)
        Ring-)L1: 异步更新本地精确缓存
    end
```

## 二、 Redis 7.x 向量与元数据存储模型 (RediSearch Schema)

在 Redis 7.x 中创建 RediSearch 索引，强制将租户标识与 ACL 设置为可快速过滤的 `TAG` 类型：

```redis
FT.CREATE idx:semantic_cache ON HASH
PREFIX 1 cache:doc:
SCHEMA
  tenant_id TAG NOINDEX CASESENSITIVE
  acl_scope TAG CASESENSITIVE
  model_family TAG CASESENSITIVE
  query_text TEXT NOSTEM
  response_payload TEXT NOINDEX
  created_at NUMERIC SORTABLE
  ttl_expires NUMERIC SORTABLE
  embedding VECTOR HNSW 6
    TYPE FLOAT32
    DIM 1536
    DISTANCE_METRIC COSINE
    M 16
    EF_CONSTRUCTION 200
```

### 1. 租户安全强制预过滤查询语句 (Mandatory Pre-Filtering)
检索时必须强制拼接租户与权限过滤子句，**严禁无租户约束的裸 KNN 检索**：
$$\text{Query} = \left(@\text{tenant\_id}:\{\text{tenant\_001}\} \ @\text{acl\_scope}:\{\text{public}|\text{vip}\}\right) \Rightarrow [\text{KNN } 1\ \text{@embedding } \$vec\ \text{AS score}]$$

## 三、 语义反漂移与命名实体（NER）极性校验算法 (Anti-Drift Guard)

```mermaid
flowchart TD
    Candidate["L2 HNSW 召回的候选问答对 (Cosine >= 0.95)"] --> PolarityCheck["否定极性比对 (Negation Polarity Check)"]
    
    PolarityCheck --> NegationExtract["提取输入 Query 与候选样本中的否定算子 (不, 未, 严禁, not, no, never)"]
    NegationExtract --> ComparePolarity{"极性是否完全一致?\n(例如: 同为肯定 或 同为否定)"}
    
    ComparePolarity -->|"否 (极性突变，如: 一个支持/一个不支持)"| Reject1["【安全拦截】判定 Cache Miss，透传上游\n(杜绝致命逻辑颠倒)"]
    
    ComparePolarity -->|"是 (极性一致)"| NERCheck["电商关键命名实体比对 (Key Named Entities Check)"]
    
    NERCheck --> ExtractEntities["提取关键业务实体: SKU 型号、国家 ISO 码、时效天数、币种"]
    ExtractEntities --> CompareEntities{"实体集合是否 100% 严格吻合?"}
    
    CompareEntities -->|"否 (实体冲突，如: US 仓误命中 UK 仓)"| Reject2["【实体冲突】判定 Cache Miss，透传上游"]
    
    CompareEntities -->|"是 (完全一致)"| Accept["【校验通过】允许命中缓存下发 (耗时 <= 15ms)"]
```

## 四、 Prompt 四层物理对齐编排模型 (Prompt Caching Alignment)

为了激发 OpenAI、Claude、DeepSeek 底层的 K-V Cache 复用机制（节约高达 80% 输入 Token 成本），网关强制规范 Prompt 的物理编排顺序：

```text
┌────────────────────────────────────────────────────────────────────────┐
│  第 1 层：静态系统角色指令 (Static System Persona)                     │
│  - 纯静态全局提示词，严禁插入时间戳或用户会话 ID                       │
│  - 长度严格对齐 >= 1024 tokens（满足云厂商 Prompt Cache 起步阈值）       │
├────────────────────────────────────────────────────────────────────────┤
│  第 2 层：静态工具声明定义 (Static Tools / Function Schemas)            │
│  - 所有可调用工具的 JSON Schema 定义                                   │
│  - 强制按工具名称字符字典序（Alphabetical Sort）稳定排列               │
├────────────────────────────────────────────────────────────────────────┤
│  第 3 层：半静态业务背景知识 (Semi-Static Few-Shots & RAG Context)      │
│  - 业务标准政策知识、少样本示例（Few-Shot Examples）                   │
│  - 相同意图下的上下文保持物理前缀稳定                                  │
├────────────────────────────────────────────────────────────────────────┤
│  第 4 层：动态历史与末尾用户提问 (Dynamic History & User Query)         │
│  - 历史多轮对话记录（最近 N 轮）                                      │
│  - 终端买家当前最新输入（Dynamic Suffix 追加在尾部）                   │
└────────────────────────────────────────────────────────────────────────┘
```

## 五、 LMAX Disruptor 异步双时钟记账与 ClickHouse 模型

为避免记账 I/O 阻塞主数据面，采用高性能无锁 Disruptor 环形队列异步排空：

```mermaid
classDiagram
    class BillingRingBuffer {
        -RingBuffer~TokenBillingEvent~ ringBuffer
        +publishEvent(GatewayContext ctx, UsageMetrics usage)
    }

    class TokenBillingEvent {
        +String tenantId
        +String traceId
        +String model
        +long promptTokens
        +long completionTokens
        +long cachedTokens
        +double actualCostUsd
        +double savedCostUsd
        +long timestampMs
    }

    class ClickHouseBatchConsumer {
        -List~TokenBillingEvent~ buffer
        +onEvent(TokenBillingEvent event, long sequence, boolean endOfBatch)
        +flushToClickHouse()
    }

    BillingRingBuffer o-- TokenBillingEvent
    ClickHouseBatchConsumer ..> TokenBillingEvent : batch processes
```

### ClickHouse 高性能审计对账表 DDL 规范：
```sql
CREATE TABLE llm_token_billing_log (
    tenant_id LowCardinality(String),
    trace_id String,
    model LowCardinality(String),
    provider LowCardinality(String),
    prompt_tokens UInt32,
    completion_tokens UInt32,
    cached_tokens UInt32,
    actual_cost_usd Float64,
    saved_cost_usd Float64,
    ttft_ms UInt32,
    status_code UInt16,
    event_time DateTime64(3, 'UTC')
) ENGINE = MergeTree()
PARTITION BY toYYYYMM(event_time)
ORDER BY (tenant_id, event_time, trace_id)
TTL event_time + INTERVAL 365 DAY;
```

## 六、 交付与测试追踪矩阵 (Traceability Matrix)

| 需求编号 | 功能项 | 验证场景与渗透测试手段 | 预期断言指标 |
| :--- | :--- | :--- | :--- |
| **FR-01** | L1~L3 递进式缓存 | 并发注入 1000 笔相同意图查询 | 首笔穿透，后续 999 笔 100% 缓存命中，端到端耗时 P99 $\le 15\text{ms}$ |

| **FR-03** | 语义反漂移 | 测试“支持跨境包邮吗”与“不支持跨境包邮吗”两个 Query | 肯定句命中缓存，否定句触发极性冲突被安全拦截并穿透 |
