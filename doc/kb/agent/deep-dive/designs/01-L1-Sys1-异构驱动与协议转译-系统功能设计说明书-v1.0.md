## 零、 模块定位与执行拓扑 (Module Positioning & Topology)

系统 1 在全局 Master Pipeline 中承担**“协议归一化（Northbound Inbound）”**与**“异构驱动调度（Southbound Outbound）”**的双向职责：
* **北向输入**：接收客户端符合 `CanonicalChatRequest` 规范的标准报文；
* **南向输出**：根据系统 2 决选的物理端点，调度对应的 `ModelDriver` 插件，将请求转译为特定供应商（OpenAI、Claude、DeepSeek、Gemini）的原生报文；
* **流式反向归一**：将上游流式返回的异构 Chunk 零拷贝解析并包装为标准内部 `StreamFrame`，独立剥离 `reasoning_content` 思维链。

### 1. 驱动加载与注册机制
* **动态发现（Spring SPI）**：利用 Spring 容器的 `@ConditionalOnProperty` 与统一接口自动装配，所有实现 `ModelDriver` 的组件在网关启动时自动注册到 `ModelDriverRegistry`；
* **只读查找性能**：注册表底层使用不可变哈希表 `Map<String, ModelDriver>`，运行时查找复杂度为 $O(1)$，全程无读写锁争用。

## 三、 深度思考模型思维链（Reasoning）分流时序与缓冲模型

针对 DeepSeek-R1、Claude 3.7 Thinking 等具备思维链的模型，驱动层必须执行**物理分流**，严禁与正式回答文本混淆：

```mermaid
sequenceDiagram
    autonumber
    participant Upstream as 上游大模型 (DeepSeek-R1)
    participant Driver as 系统 1: 驱动层 (DeepSeekDriver)
    participant StreamPipe as 系统 4: 流式管道
    participant Downstream as 下游客户端 (Web / App)

    Upstream-->>Driver: raw_chunk: {"choices":[{"delta":{"reasoning_content":"先分析用户意图..."}}]}
    Driver->>Driver: 捕获 reasoning_content 字段，包装为 FrameType=REASONING_CHUNK
    Driver-->>StreamPipe: emit(StreamFrame: REASONING)
    
    alt 客户端声明支持思维链 (X-Support-Reasoning: true)
        StreamPipe-->>Downstream: event: reasoning\ndata: {"content": "先分析用户意图..."}\n\n
    else 客户端为老旧普通客户端 (默认)
        StreamPipe->>StreamPipe: 缓冲/包裹为 Markdown 折叠标签 (<details><summary>思考过程</summary>...</details>)
        StreamPipe-->>Downstream: event: message\ndata: {"content": "<details><summary>思考过程</summary>先分析用户意图..."}\n\n
    end

    Upstream-->>Driver: raw_chunk: {"choices":[{"delta":{"content":"这是正式回答。"}}]}
    Driver->>Driver: 捕获 content 字段，包装为 FrameType=TEXT_CHUNK
    Driver-->>StreamPipe: emit(StreamFrame: TEXT)
    StreamPipe-->>Downstream: event: message\ndata: {"content": "这是正式回答。"}\n\n
```

## 四、 动态多 Key 凭据池与 429 冷却自愈状态机 (Key Pool State Machine)

为解决企业单 Key 极易触发供应商频控的问题，每个供应商维护一个线程安全的动态 Key 资源池：

```mermaid
stateDiagram-v2
    [*] --> ACTIVE: 初始化装载 (Weight = W, InFlight = 0)
    
    ACTIVE --> ACTIVE: 加权轮询调度 (Round-Robin / Least In-Flight)
    ACTIVE --> COOLDOWN: 收到上游 HTTP 429 或 401 报文
    
    state COOLDOWN {
        [*] --> Sleeping: 记录冷却起始时间 (设置 TTL = max(Retry-After, 60s))
        Sleeping --> ProbeReady: 倒计时归零
    }
    
    COOLDOWN --> PROBING: 发起异步微型探测请求 (Minimal Ping Prompt)
    
    PROBING --> ACTIVE: 探测成功 (HTTP 200) -> 恢复全量调度
    PROBING --> COOLDOWN: 探测失败 (仍为 429) -> 冷却时间翻倍 (指数退避)
    
    ACTIVE --> DISABLED: 管理端手动下线 Key
    COOLDOWN --> DISABLED: 管理端手动下线 Key
    DISABLED --> [*]
```

### 调度算法参数模型：
* **调度选择器**：计算每个活跃 Key 的得分：
  $$\text{KeyScore}_i = \frac{\text{CurrentInFlight}_i + 1}{\text{ConfiguredWeight}_i}$$
  每次调用优先挑选 $\text{KeyScore}$ 最小的可用 Key，实现动态负载均衡。

## 五、 本地高精度 BPE 分词与上下文滑动窗口预截断算法

为了在不消耗网络 RTT 的前提下完成 Token 预估并防止上下文超限，集成高性能本地分词算法：

```mermaid
flowchart TD
    Start["入站 CanonicalChatRequest"] --> BPE["本地 BPE 分词器 (TikToken / Byte-Pair Encoding)"]
    BPE --> Count["计算总 Token 数: PromptTokens = Sum(BPE(messages)) + ToolsTokens"]
    Count --> Check{"PromptTokens <= ModelContextLimit?"}
    
    Check -->|"是 (未越界)"| Pass["放行流转至下一 Filter"]
    
    Check -->|"否 (上下文溢出)"| PolicyCheck{"租户配置的截断策略"}
    
    PolicyCheck -->|"策略 A: REJECT (严格阻断)"| Err["抛出标准 400 CONTEXT_WINDOW_EXCEEDED 错误"]
    PolicyCheck -->|"策略 B: SLIDING_WINDOW (智能截断)"| Truncate["执行滑动窗口裁剪算法"]
    
    Truncate --> KeepSystem["1. 强制保留 System Prompt"]
    KeepSystem --> KeepTools["2. 强制保留 Tools/Function Schema"]
    KeepTools --> KeepLatest["3. 保留最新 2 轮对齐的 User-Assistant 对话"]
    KeepLatest --> DropOld["4. 从早期历史消息自前向后逐条修剪 (Drop Earliest Messages)"]
    DropOld --> MarkHeader["5. 注入响应头 X-Context-Truncated: true 并放行"]
```

## 八、 面向开发、QA、SRE 与 AI 的落地指引

* **对后端研发**：根据 `ModelDriver` 接口规范与映射表编写各供应商 Driver，严格使用 Netty `ByteBuf` 切片解析，禁止动态反射；
* **对 QA 测试**：根据映射矩阵编写单元测试与参数边界测试（重点测试 Claude 的 1.0 截断、System Prompt 剥离）；
* **对 SRE 运维**：通过 Nacos 动态更新 `key_credentials_pool` 配置，监控 Key 状态机指标 `llm_gateway_key_status`；
* **对 AI 编码引擎**：将本设计书作为上下文，逐驱动类（如 `DeepSeekDriver.java`）进行 TDD 单元测试与类结构生成。
