## 零、 模块定位与数据面拓扑 (Module Positioning & Topology)

系统 4 是 L1 LLMOps 网关的**“数据面非阻塞传输管道与长连接安全内核”**。它处于大模型异构推理集群（上游）与全球分布式买家终端（下游）之间：
* **快产慢消物理制动**：在上游生产速率（100t/s）与下游移动弱网消费速率（3t/s）严重失配时，**以内核级 Socket 发送缓冲区水位反向制动上游 HTTP/2 流量控制，实现绝对 Zero-OOM**；
* **客户端断网毫秒级级联取消**：当用户关闭浏览器或 App 闪退时，在 **$\le 5\text{ms}$** 内向上游发送 HTTP/2 `RST_STREAM`，掐断无效计算，避免 Token 巨额浪费；
* **流式跨分块实时内容安全**：基于 Aho-Corasick 多模式自动机与双端字符滑动窗口，在流式吐字的同时实时拦截敏感违规词。

## 一、 内核套接字背压传导与状态流转时序图 (Backpressure Sequence Flow)

```mermaid
sequenceDiagram
    autonumber
    participant Downstream as 慢客户端 (移动弱网 3t/s)
    participant NettyChannel as 网关下行 Netty Channel (Socket 发送缓冲区)
    participant BackpressureHandler as 系统 4: 背压协调处理器
    participant UpstreamClient as 上游 Netty HttpClient (HTTP/2 流)
    participant UpstreamLLM as 上游大模型集群 (100t/s 狂吐)

    UpstreamLLM-->>UpstreamClient: 高速发射数据帧 (Data Frames)
    UpstreamClient-->>BackpressureHandler: 接收 ByteBuf 数据块
    BackpressureHandler->>NettyChannel: writeAndFlush(ByteBuf)
    
    Note over NettyChannel,Downstream: 客户端消费极慢，内核 TCP 发送缓冲区迅速堆积
    NettyChannel->>NettyChannel: 缓冲区达到高水位线 (High Watermark: 64KB)
    NettyChannel->>BackpressureHandler: 触发 ChannelWritabilityChanged (isWritable = false)
    
    BackpressureHandler->>UpstreamClient: 立即反向制动: 暂停调用 channel.read()\n不再向上游发送 HTTP/2 WINDOW_UPDATE 帧
    Note over UpstreamClient,UpstreamLLM: 上游 HTTP/2 连接窗口耗尽 (Stream Window Exhausted)，上游推理集群暂停网络发包！
    
    Note over Downstream: 客户端网络恢复，缓慢读取了 32KB 数据
    NettyChannel->>NettyChannel: 发送缓冲区回落至低水位线 (Low Watermark: 32KB)
    NettyChannel->>BackpressureHandler: 触发 ChannelWritabilityChanged (isWritable = true)
    
    BackpressureHandler->>UpstreamClient: 恢复流转: 恢复 channel.read()\n向上游补发 HTTP/2 WINDOW_UPDATE 扩容帧
    UpstreamLLM-->>UpstreamClient: 上游恢复发射后续 Token
```

## 二、 固定 32KB 环形缓冲 Zero-OOM 数据模型 (Memory Bound Model)

为了保障万级并发长连接下 Pod 内存绝对平稳，单连接缓冲区受到严格的物理边界约束：

```mermaid
classDiagram
    class ConnectionStreamBuffer {
        -int highWatermark = 65536 // 64KB
        -int lowWatermark = 32768  // 32KB
        -AtomicLong pendingBytes
        -AtomicBoolean isPaused
        +onWrite(ByteBuf chunk)
        +onFlushSuccess(int bytes)
        +checkWritability() boolean
    }

    class StreamFramePool {
        -PooledByteBufAllocator allocator
        +acquire(int size) ByteBuf
        +release(ByteBuf buf)
    }

    ConnectionStreamBuffer o-- StreamFramePool
```

### 内存有界性数学证明：
设单 Pod 承载 $N$ 个并发活跃长连接，每个连接在最极端的阻塞状态下最多积压一个高水位阈值的数据量：
$$\text{MaxDirectMemory} = N \cdot \text{HighWatermark} = 10,000 \times 64\text{KB} = 640\text{MB}$$
在 4GB 物理内存容器中，缓冲区常驻内存仅占 **$16\%$**，数学上彻底杜绝内存无底洞堆积导致的 `OOMKilled`。

## 三、 客户端断网级联取消全链路时序图 (Cascade Cancellation)

```mermaid
sequenceDiagram
    autonumber
    actor User as 用户 (移动终端)
    participant ClientSocket as 客户端套接字
    participant Gateway as 网关流式引擎 (Sys 4)
    participant UpstreamLLM as 上游推理集群 (OpenAI / vLLM)

    User->>ClientSocket: 用户强退 App 或切入电梯弱网完全失联
    ClientSocket->>Gateway: 发送 TCP FIN 报文或网关心跳探针判定失联
    
    Gateway->>Gateway: 捕获 Netty channelInactive() 事件\n(耗时 <= 1ms)
    
    Gateway->>Gateway: 触发响应式管道 Subscription.cancel()
    Gateway->>UpstreamLLM: 立即向上游连接发送 HTTP/2 RST_STREAM 帧 (Error Code = CANCEL)
    
    Note over UpstreamLLM: 上游推理引擎捕获 RST_STREAM，立即中止 GPU 显存解码！\n(全链路总耗时 <= 5ms)
    Gateway->>Gateway: 释放当前连接的所有堆外 ByteBuf 引用，归还连接池
```

## 四、 Aho-Corasick 多模式自动机流式跨分块审查算法 (Stream AC Automaton)

针对大模型边生成边吐字时，不良词汇可能跨 Chunk 拼接逃逸的问题，维护固定大小的字符滑动窗口：

```mermaid
flowchart TD
    InChunk["上游到达的流式 Chunk (如 '感词')"] --> RingWindow["追加到双端字符滑动窗口 (Sliding Character Ring)"]
    
    RingWindow --> ACTrie["Aho-Corasick 多模式自动机 (内存 Trie 树)"]
    
    ACTrie --> StateTransition["根据当前字符执行状态转移 (State = State.next[char] || State.fail)"]
    
    StateTransition --> MatchCheck{"是否命中敏感词终态节点 (isTerminal)?"}
    
    MatchCheck -->|"否 (合规正常)"| PassThrough["向客户端下发当前 Chunk: data: {'content': '...'}"]
    
    MatchCheck -->|"是 (命中违规词)"| ImmediateKill["【安全阻断】立即掐断流式传输！"]
    ImmediateKill --> CancelUpstream["1. 向上游下发 RST_STREAM 中止推理"]
    ImmediateKill --> SanitizeEmit["2. 向客户端下发安全替换话术:\n'抱歉，该内容涉及合规限制，已为您终止生成。'"]
    ImmediateKill --> LogAudit["3. 记录敏感词违规审计日志并上报安全风控大盘"]
```

## 五、 激进心跳探测与长连接保活机制 (Aggressive KeepAlive)

为了防止中间设备（如 AWS ALB、NAT 网关、家庭路由器）在模型长思考期间因 60s 空闲超时而掐断 TCP 连接：
1. **SSE 注释空行心跳（Application Ping）**：
   * 网关启动定时调度器，若某长连接持续 **15 秒** 未产生任何有效 Token；
   * 网关主动向客户端下发一行 W3C 标准的 SSE 注释行：`:keep-alive\n\n`；
   * 客户端标准 SSE 接收器会自动忽略注释行，但整个网络物理链路的 Idle 计时器被成功重置。
2. **TCP 保活探针（Transport KeepAlive）**：
   * 开启套接字底层 `SO_KEEPALIVE`，设置探测参数：`tcp_keepalive_time=30`，`tcp_keepalive_intvl=5`，`tcp_keepalive_probes=3`。
