## 第一章：基于 ASD-STE100 规范的死循环熔断与算力预算工程技术标准

本章节遵循国际工业与航空标准 **ASD-STE100（Simplified Technical English）** 编写。旨在通过严格受控词汇、短句结构（$\le 20$ 词）与主动语态，消除跨国开发、运维排障与财务核算团队的技术理解歧义。

### SECTION 1: PURPOSE AND DEFINITIONS / 目的与术语定义

#### STE English:
1. This section gives mandatory rules to stop infinite loops and budget overruns in Hook 3.
2. **Infinite Loop**: A failure state where an agent continuously calls an AI model without stopping.
3. **Logic Wall-Hit**: A condition where a model hallucinates and retries wrong tool parameters repeatedly.
4. **Consecutive Tool Failure**: Multiple sequential errors returned by the same tool within one run.
5. **Circuit Breaker**: A software control that stops execution when error thresholds are exceeded.
6. **Two-Phase Quota Reservation**: A process that locks token budget before model inference and settles afterwards.
7. **Wall-Clock Timer**: A physical hardware-clock monitor that stops a network request when time expires.

#### 标准中文对照：
1. 本章节给出在 Hook 3 中阻止死循环与预算超支的强制性工程规则。
2. **死循环（Infinite Loop）**：Agent 不受控制地持续调用 AI 模型且无法退出的故障状态。
3. **逻辑鬼打墙（Logic Wall-Hit）**：模型因产生幻觉而反复重试错误工具参数的异常状态。
4. **连续工具错误（Consecutive Tool Failure）**：在单次运行中同一工具连续返回多次错误。
5. **断路器（Circuit Breaker）**：当错误超过设定阈值时强行终止执行的软件控制机制。
6. **两阶段配额预占（Two-Phase Quota Reservation）**：在模型推理前锁定 Token 预算并在推理后平账的过程。
7. **物理绝对时钟定时器（Wall-Clock Timer）**：当物理时间到期时强行终止网络请求的硬件时钟监控器。

---

### SECTION 2: OPERATIONAL INVARIANTS FOR MODEL CALLS / 模型调用操作不变量与治理约束

#### STE English:
1. The harness must not permit the language model to decide loop termination alone.
2. The harness must maintain a hard ceiling for total execution steps in each run.
3. If a tool fails three consecutive times, the harness must trip the circuit breaker immediately.
4. When the circuit breaker trips, the harness must revoke tool retry permissions from the model.
5. In Hook 3, the harness must deduct estimated token costs in Redis before the network call.
6. If the tenant token balance is less than the estimated cost, the harness must abort the run.
7. The harness must attach a 30-second wall-clock timer to every outbound model connection.
8. If the timer expires, the harness must send an HTTP/2 `RST_STREAM` frame to the gateway.
9. Do not trust the model to report its own token consumption accurately.
10. Do not configure a loop without both step limits and cost quotas.

#### 标准中文对照：
1. 宿主系统严禁允许大语言模型独自裁决循环的终止。
2. 宿主系统必须在每次运行中为总执行步数维护硬性上限。
3. 若某工具连续失败达到 3 次，宿主系统必须立即触发断路器。
4. 当断路器触发时，宿主系统必须剥夺大模型对该工具的重试权限。
5. 在 Hook 3 中，宿主系统在发起网络调用前必须在 Redis 中预扣减预估 Token 费用。
6. 若租户的 Token 余额小于预估费用，宿主系统必须中止本次运行。
7. 宿主系统必须为每个外呼模型连接挂载一个 30 秒的物理绝对时钟定时器。
8. 若定时器超时，宿主系统必须向下游网关发送 HTTP/2 `RST_STREAM` 错误帧。
9. 严禁信任大语言模型自主上报的 Token 消耗量。
10. 严禁配置同时缺少步数上限与费用配额的无保护循环。

### SECTION 3: STEP-BY-STEP PROCEDURE / 逐步操作规程

```
[Tool Fails] ──> [Increment Error Counter] ──> [Check Threshold >= 3] ──> [Trip Breaker] ──> [Suspend Run to Human Worktable]
```

#### STE English:
1. **Step 1 (Tool Observation)**: Capture the tool execution result and check the HTTP status code.
2. **Step 2 (Counter Evaluation)**: If the tool returns a non-business error, increment the consecutive failure counter.
3. **Step 3 (Threshold Check)**: If the failure counter equals three, execute the circuit breaker action.
4. **Step 4 (Model Interception)**: In Hook 3, stop the outbound model prompt assembly.
5. **Step 5 (Quota Rollback)**: Refund unspent reserved tokens back to the tenant Redis ledger.
6. **Step 6 (State Suspension)**: Update the run status to `SUSPENDED_FOR_HUMAN_REVIEW` in PostgreSQL.
7. **Step 7 (Alerting)**: Send an urgent notification to the human customer support queue.

#### 标准中文对照：
1. **步骤 1（工具观测）**：捕获工具执行结果并核查其 HTTP 状态码。
2. **步骤 2（计数器评估）**：若工具返回非业务逻辑错误，递增连续失败计数器。
3. **步骤 3（阈值核查）**：若失败计数器达到 3 次，执行断路器动作。
4. **步骤 4（模型拦截）**：在 Hook 3 中，终止后续外发模型 Prompt 的组装流程。
5. **步骤 5（配额回滚）**：将未消耗的预占 Token 预算退还至租户 Redis 账本。
6. **步骤 6（状态挂起）**：在 PostgreSQL 中将本次运行状态更新为 `SUSPENDED_FOR_HUMAN_REVIEW`。
7. **步骤 7（告警通知）**：向人工客服工作台队列发送紧急告警通知。

### SECTION 4: WARNINGS AND PROHIBITED ACTIONS / 警告与绝对禁止动作

#### STE English:
* **WARNING 1**: DO NOT RELY ON SIMPLE `while not task.is_completed` LOOPS IN PRODUCTION.
* **WARNING 2**: DO NOT PERMIT UNLIMITED RETRIES WHEN THIRD-PARTY APIS RETURN HTTP 400 OR 500 ERRORS.
* **WARNING 3**: LONG CONTEXT EXPANSION INCREASES TOKEN COSTS EXPONENTIALLY DURING RETRY LOOPS.
* **WARNING 4**: AN UNCHECKED INFINITE LOOP CAN DEPLETE ENTERPRISE API CREDITS IN MINUTES.

#### 标准中文对照：
* **警告 1**：严禁在生产环境中依赖简陋的 `while not task.is_completed` 循环。
* **警告 2**：当第三方 API 返回 HTTP 400 或 500 错误时，严禁允许模型无限次重试。
* **警告 3**：在重试循环期间，上下文急剧膨胀会导致单次 Token 调用费用呈指数级暴增。
* **警告 4**：未经治理的死循环可在数分钟内彻底耗尽企业的全部 API 算力余额。

## 第二章：深度剖析：为什么主流开源框架会陷入“死循环死穴”？

在开发 AI Agent 时，许多团队为了快速上线，直接基于 **AutoGPT、早期的 LangChain `AgentExecutor`、CrewAI 或 AutoGen** 搭建业务原型。这些框架在 Demo 阶段表现惊艳，但在真实的生产环境下却隐藏着致命的“死循环死穴”。

### 1. 开源框架的底层核心代码长什么样？
翻开这些开源框架早期的底层执行驱动代码，其本质逻辑几乎全部由一段极简的 Python `while` 循环构成：

```python
# 典型开源框架的底层 Agent 执行循环 (极度危险的裸奔设计)
messages = [SystemPrompt, UserPrompt]

while True:  # ⚠️ 致命死穴：完全依赖大模型自主决定退出条件
    response = llm.chat(messages)
    
    # 1. 如果大模型输出了 tool_calls，说明模型认为任务尚未完成，继续调用工具
    if response.has_tool_calls():
        tool_result = execute_tool(response.tool_calls)
        # 将报错信息拼回上下文，继续下一轮循环，让模型“自己看着办”...
        messages.append({"role": "tool", "content": tool_result})
    
    # 2. 只有当大模型明确输出“任务已完成(Final Answer)”且不再调用工具时，才跳出循环！
    else:
        return response.content
```

### 2. 为什么开源框架最初要设计成“完全依赖大模型自主决定退出”？
这源于学术界经典的 **ReAct（Reasoning + Acting，推理与动作协同）范式**。框架作者们的初衷是好的：
1. **追求极致的“智能体自治（Autonomy）”**：  
   传统业务靠工程师写死 `if-else`。而 Agent 的核心卖点就是“让 AI 像人一样聪明地自主解决问题”——遇到阻碍自主思考（Thought），尝试调用工具（Action），根据观察结果（Observation）自我修正；
2. **假设大模型具备“自我反思纠错（Self-Reflection）”能力**：  
   框架设计者的美好假设是：*“如果大模型传错了一个参数，下游工具返回了报错，大模型能读懂错误提示，并在下一轮对话里自己把参数改对。”*

### 3. 为什么这个假设在工业生产中会彻底破灭？
**因为真实世界的生产系统 Bug，绝不是靠大模型“反思”就能脑补解决的！**
* 如果下游服务网络断开、或者数据库缺字段、或者第三方 API 变更了枚举值，不管大模型智商多高、反思多少遍，下游返回的永远是冷冰冰的 `400 Bad Request`；
* **大模型的内疚与迎合心理（Sycophancy & Hallucination）**：大模型不知道下游其实是确定性的代码错误，它会产生强烈的幻觉，误以为是自己“Prompt 没写好”、“语气不对”、“JSON 缺少引号”。为了达成目标，它会不断微调微小的标点、大小写和参数命名，不知疲倦地持续重试，**绝不轻言放弃**！
* **开源框架在旁边“冷眼旁观”**：框架只认准一个死规矩——只要大模型还在发 `tool_calls`，我就继续循环。**发动机已经过热着火，油门却被死死焊死，没有任何刹车机制！**

### 为什么即使配了 `max_iterations = 100`，依然会“一夜刷爆数十万 API”？

很多工程师辩解：“我在开源框架里配一个最大重试次数 `max_iterations = 100` 不就行了吗？”  
**在真实的生产并发场景下，这根本防不住，反而会造成“长上下文费用雪崩”！**

#### 1. 上下文滚雪球效应（Context Snowball Explosion）
* 在第 1 轮时，Prompt 只有 2,000 Tokens；
* 到第 30 轮时，由于每一轮的报错历史、反思推演都被塞回 Context，对话历史迅速膨胀到 **60,000 Tokens**！
* 按照 GPT-4o 或 Claude 3.5 Sonnet 的计费标准，单次调用 60,000 Tokens 的长上下文，一次网络 I/O 成本高达 **$0.30 ~ $0.50 美元**！
* 单个工单跑完这 100 轮，累计消耗超过 **$30.00 美元**，比买家要索赔的手表补偿金（$30.00）还要贵！

#### 2. 高并发乘数效应（Multiplied Disaster）
大促期间，一小时内有 1,000 笔售后退赔工单并发进入系统。如果恰好物流 TMS 接口出现故障，1,000 个工单并发陷入这 100 次空转：
$$1,000 \text{ 个工单} \times 100 \text{ 轮循环} = 100,000 \text{ 次大模型长上下文高阶 API 轰炸！}$$
短短数小时内，数万美元的算力额度瞬间归零，企业在 OpenAI / Anthropic 的主账户直接因欠费被**全局停机（Account Suspended）**，导致全公司所有基于大模型的售前导购、营销文案、智能客服全站瘫痪！

## 第四章：企业级微内核架构对策：Harness 的三道物理硬核枷锁

在我们的专题 [11-Hook3-before_model-算力原子预算预占与死循环硬熔断落地实战](file:///Users/allen/Desktop/NewArchitect/workspace/cogniva/doc/kb/agent/deep-dive/topics/01-lifecycle-hooks/11-Hook3-before_model-算力原子预算预占与死循环硬熔断落地实战.md) 中，控制环提出了绝对底线：**“绝对把最高控制权握在操作系统级宿主（Harness）手中，绝不向概率论大模型让渡决定何时终止的主权！”**

我们在 Hook 3（`before_model`）外呼前构建了 **三道硬核物理防线**：

```
                    【大模型网络外呼前 (before_model 准入拦截)】
                                     │
      ┌──────────────────────────────┼──────────────────────────────┐
      ▼                              ▼                              ▼
【枷锁 1：连续错误断路器】     【枷锁 2：Redis Lua 原子预占】  【枷锁 3：物理 Wall-Clock 定时器】
若检测到同一个工具连续报错    为单笔退赔工单硬核分配           设置物理绝对超时 (如 30 秒)。
超过 3 次 (非业务性 4xx/5xx)， 最大预算 $0.50。               超时直接发送 HTTP/2 RST 报文
宿主直接判定“下游依赖死锁”，   在 Redis 原子扣减，一旦超支，   硬掐断底层网络流，
立刻剥夺大模型重试权，         抛出 QuotaExceededException，   绝不让线程挂死空转！
强行终止并转人工工单！         物理熔断出网通道！
```

### 1. 枷锁一：连续工具错误断路器（Consecutive Failure Breaker）
Harness 内核维护一个局部状态机。如果某个工具（如 `query_shipping_fee`）连续返回非业务层面的系统错误（HTTP 400、500、连接超时）达到 **3 次**：
* 宿主判定“系统级故障，大模型绝无可能自我修复”；
* **物理剥夺模型的调用资格**，不再把错误抛回给模型反思，而是直接熔断跳出控制环，将状态机置为 `SUSPENDED_FOR_HUMAN_REVIEW`，转交人工客服处理。

### 2. 枷锁二：两阶段 Redis Lua 算力原子预占（Two-Phase Quota Barrier）
* **事前原子扣减**：在发请求给大模型前，基于 Prompt 长度预估消耗，执行 Redis Lua 脚本预扣减配额（单笔工单硬顶 **$0.50 美元** 或 **10,000 Tokens**）；
* **欠费当场熔断**：一旦工单因为重试导致预算耗尽，Lua 脚本直接返回 `-1`，Harness 抛出 `QuotaExceededException`，网络请求在内网网关当场被扼杀，不向外网发送一个字节！
* **事后精准平账**：调用返回后，根据模型真实计费 Token 数量退还多扣的额度（多退少补）。

### 3. 枷锁三：物理绝对时钟定时器与 HTTP/2 RST_STREAM
* 挂载内核级 `ScheduledExecutorService` 硬件定时器（严格限时 30 秒）；
* 若大模型服务端因拥堵假死或推理超时，定时器触发，**立即向外部 HTTP/2 连接发送 `RST_STREAM` 错误帧，强行关闭底层 TCP Socket**；
* 彻底释放本地 Worker 线程与远程 GPU 解码算力，绝不让无效请求在后台静默耗电。

## 第五章：生产级双语实现源码（Java 21 范式）

以下代码演示了在 Harness 控制环中，`before_model` 如何通过连续错误熔断器守死底层防线：

```java
package com.cogniva.agent.harness.circuitbreaker;

import java.util.Map;
import java.util.Objects;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.atomic.AtomicInteger;

/**
 * Hook 3 before_model 核心防线：连续工具错误断路器
 */
public final class ConsecutiveToolFailureCircuitBreaker {

    private final String runId;
    private final int maxAllowableFailures; // 硬阈值，默认 3 次
    
    // 工具名 -> 连续失败次数计数器
    private final Map<String, AtomicInteger> failureCounters = new ConcurrentHashMap<>();

    public ConsecutiveToolFailureCircuitBreaker(String runId, int maxAllowableFailures) {
        this.runId = Objects.requireNonNull(runId);
        this.maxAllowableFailures = maxAllowableFailures;
    }

    /**
     * 当工具执行返回结果时被控制环调用
     * @param toolName 工具名称 (如 "query_shipping_fee")
     * @param isSystemError 是否为系统级不可自愈错误 (HTTP 4xx, 5xx, Timeout)
     */
    public void recordToolExecution(String toolName, boolean isSystemError) {
        AtomicInteger counter = failureCounters.computeIfAbsent(toolName, k -> new AtomicInteger(0));
        
        if (isSystemError) {
            int currentFailures = counter.incrementAndGet();
            if (currentFailures >= maxAllowableFailures) {
                // 【触发硬熔断】：剥夺大模型重试权，强行掐断循环
                throw new ToolDependencyDeadlockException(String.format(
                    "CIRCUIT BREAKER TRIPPED: Tool [%s] failed [%d] consecutive times in Run [%s]. Downstream dependency deadlocked. Revoking model retry autonomy!",
                    toolName, currentFailures, runId
                ));
            }
        } else {
            // 工具调用成功，重置连续错误计数器
            counter.set(0);
        }
    }

    /**
     * 在 Hook 3 before_model 发送请求前，核验该工具是否已被熔断锁定
     */
    public void assertToolExecutable(String toolName) {
        AtomicInteger counter = failureCounters.get(toolName);
        if (counter != null && counter.get() >= maxAllowableFailures) {
            throw new ToolDependencyDeadlockException("Tool [" + toolName + "] is locked by circuit breaker.");
        }
    }
}
```
