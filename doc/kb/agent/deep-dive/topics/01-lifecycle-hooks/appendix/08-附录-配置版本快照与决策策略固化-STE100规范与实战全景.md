## 零、 痛点全景：长周期任务遭遇“配置热漂移（Configuration Drift）”的致命车祸

在跨境电商售后争议调解场景中，一个工单从买家提交到最终资金划转往往是一个**跨越数小时的长周期流程（Long-running Workflow）**。

若缺乏“配置快照固化”机制，运营或运维在中途热更新配置，将直接引发 Agent 的**“逻辑精神分裂”与资损车祸**：

```
时间线 (t)    买家 / 流程执行节点                       运营与配置中心后台                   底层资金支付与规则校验网关
  │
 t0 ──► 买家发起户外智能手表售后 ($180)
  │     [Step 1: 视觉质检与运费核算]
  │     - 读取当时配置: "运费>$35且划痕轻微，允许仅退款"
  │     - 模型判定: "赔付 $50"
  │     - 触碰 $50 审批红线，进入挂起态 (SUSPENDED)
  │     - 任务进入飞书/企微，等待主管审批
  │                    │
 t1 ───────────────────┼────────────────────────► 运营发现今日退款预算超标！
  │                    │                          紧急在后台热更新配置：
  │                    │                          1. Prompt 改为: "手表类目严禁仅退款，必须退货入海外仓"
  │                    │                          2. 风控限额: 仅退款上限从 $50 骤降为 $30
  │                    │
 t2 ──► 【2小时后：主管在企微点击同意赔付 $50】
  │     - 调度系统唤醒 Agent 恢复执行
  │     │
  │     ├────────────────────────────────────────┬────────────────────────────────────────┐
  │     ▼ (传统裸跑 Agent: 动态读取最新配置)     ▼ (落地 Harness 门禁: 固化配置快照)
  │     - 读到新 Prompt: "禁止仅退款"            - 读取固化的 FrozenRunContext (v2.4.1)
  │     - 思维链产生逻辑撕裂，推翻前序主管决定   - 严格遵循 t0 时刻签署的判定基线
  │     - 强行调底层退款时触发 $30 校验异常崩溃   - 顺利调起 Stripe 完成 $50 划付
  │     - 造成买家投诉升级与工单死锁             - 生成 Merkle 审计收据，权责分明
```

## 一、 第一步：功能五与功能六在分布式系统知识图谱中的理论映射

在 [01-分布式系统架构体系全景知识图谱-v1.0.md](../../../../../distributed-systems/01-分布式系统架构体系全景知识图谱-v1.0.md) 中，Hook 1 的“状态反水化（功能五）”与“策略快照固化（功能六）”是运行时控制与容错体系的关键基石：

```
                         【分布式系统六大根基支柱】
                                     │
           ┌─────────────────────────┼─────────────────────────┐
           ▼                         ▼                         ▼
   【支柱 IV: 存储与数据】   【支柱 V: 容错与韧性】    【支柱 III: 运行时控制】
   * 检查点快照存储          * 故障转移接管状态自愈    * 长周期断点续跑 (Resume Run)
   * 状态数据持久化          * 杜绝老节点脏写          * 策略版本固化 (Policy Freeze)
```

1. **分布式存储与数据管理（支柱 IV）**：  
   `on_run_load` 必须依赖底层分布式快照。小状态存入 PostgreSQL JSONB，海量多模态数据转存 S3/MinIO。
2. **分布式容错与韧性工程（支柱 V）**：  
   在节点发生硬件崩溃或 K8s 漂移时，备用 Worker 通过最后一份带有单调 `fencing_token` 的检查点安全接盘，实现秒级故障转移（Failover Recovery）。
3. **分布式运行时控制与生命周期（支柱 III）**：  
   针对人机协同（HITL）主动挂起数小时的任务，通过不可变上下文 `FrozenRunContext` 锁定策略，保证在分布式集群多节点流转过程中，决策边界**不因节点切换或时间推移而发生热漂移**。

## 二、 第二步：结合真实电商场景深度解构功能六

以 [02-跨境电商售后争议退赔Agent-控制环与防重对账-STAR-L实战.md](../02-跨境电商售后争议退赔Agent-控制环与防重对账-STAR-L实战.md) 中的高客单价跨境纠纷为例：

### 1. 什么是“配置版本快照（Config Snapshot）”？
在 `on_run_load` 拾取到任务的瞬间，Worker 从配置中心读取商户当前生效的**静态数据全量切片**：
* `config_snapshot_hash`：策略配置内容的 SHA-256 唯一摘要；
* `prompt_template_version`：例如 `prompt:dispute_resolution:v2.4.1`（包含提示词正文与参数定义）；
* `model_spec`：精确固化的大模型规格：`model_id: "claude-3-5-sonnet@20241022"`, `temperature: 0.0`, `seed: 42`；
* `risk_policy`：退赔硬性指标：`{"max_auto_refund_limit": 50.00, "allow_keep_item_threshold": 35.00}`；
* `tool_whitelist_hash`：允许调用的工具清单（Stripe 支付、发券工具）的 SHA-256 校验码。

### 2. 什么是“决策策略固化（Policy Freezing）”？
将抓取到的配置装配为全局只读的 `FrozenRunContext` 对象，注入该 Run 的运行时。  
**核心铁律**：该配置在当前 Run 全生命周期内（从开始到 Finalize）**绝对禁止二次热更新**。运营后台修改规则，**仅对修改时刻之后新创建的 Run 生效**，当前正在运行或因等待审批挂起的 Run 全程免疫。

### 3. 深入剖析三大核心质量保障

| 质量保障维度 | 本质定义 | 智能手表 ($180) 售后争议实战场景体现 |
| :--- | :--- | :--- |
| **确定性<br>(Determinism)** | **“推理世界观与决策边界恒定”**：输入固定、历史固定时，推理逻辑前后自洽，不随执行跨度产生漂移。 | 质检 Step 1 判定赔付 $50 的依据是“当时运费高且允许仅退款”。确定性保证了哪怕等待人工审批耽搁了 2 小时，Agent **前后的判定逻辑一致**，绝不会在前半截说“赔 $50”，审批通过后醒来突然改口说“违反新规定不能赔”。 |
| **可审计性<br>(Auditability)** | **“具备法律和财务级对账凭据”**：每一步行为都有据可查，责任边界清晰，杜绝糊涂账。 | 月末对账时，商户财务质问平台：“这笔 $50 仅退款谁批准的？为什么直接扣我账户？”审计系统直接出示 `config_snapshot_hash`，证明决策完全符合商户在 11 月 1 日签署启用的 `v2.4.1` 政策，**权责清晰，消灭平台与商户扯皮**。 |
| **可复现性<br>(Reproducibility)** | **“支持单步历史时间旅行回放（Deterministic Playback）”**：能够在沙箱中 100% 还原事故现场。 | 某天出现了一笔可疑退款怀疑遭遇提示词越狱。安全工程师在测试沙箱中，注入当时的买家证据图、固化的 `prompt_version`、固定 seed 和模型版本，**100% 像素级复现当时的推理思维链与工具调用**，让注入漏洞无所遁形。 |

## 三、 第三步：ASD-STE100 规范标准英文技术解构

> **ASD-STE100 规范核心准则**：
> 1. 每句限一个技术指令或事实，长度不超过 20 个单词；
> 2. 必须使用受控词汇（Approved Words），杜绝代词模糊指代；
> 3. 严禁使用被动语态，统一采用主动语态。

### 1. IDENTIFICATION / 概念识别
```
- Policy snapshot freezing is an operation that locks configuration data for one agent run.
- The worker executes this operation during the on_run_load lifecycle gate.
- The snapshot contains the prompt version, model parameters, and risk limits.
```
* **中文对照**：
  * 策略快照固化是指为一个 Agent 运行锁定配置数据的操作。
  * 工作节点在 `on_run_load` 生命周期门禁期间执行此操作。
  * 快照包含提示词版本、模型参数和风控限额。

### 2. TECHNICAL PROBLEM / 痛点与危险
```
- An agent run can wait for two hours for human approval.
- An operator can change the prompt template or refund limits during this time.
- If the configuration changes during the run, the agent logic becomes unstable.
- The agent can use different decision rules for step one and step three.
- This condition causes system errors, state corruption, and financial loss.
```
* **中文对照**：
  * Agent 运行可能需要等待两小时的人工审批。
  * 在此期间，运营人员可能会更改提示词模板或退款限额。
  * 如果配置在运行期间发生变化，Agent 逻辑将变得不稳定。
  * Agent 可能会在步骤一和步骤三中使用不同的决策规则。
  * 这种情况会导致系统错误、状态损坏和资金损失。

### 3. TECHNICAL SOLUTION / 技术方案
```
- The worker must read the active policy configuration at the start of the run.
- The worker must calculate a cryptographic SHA-256 hash of this configuration.
- The worker must write this data into the immutable run context.
- The agent must use only this frozen context during its full life cycle.
```
* **中文对照**：
  * 工作节点必须在运行开始时读取当前生效的策略配置。
  * 工作节点必须计算该配置的 SHA-256 加密哈希值。
  * 工作节点必须将这些数据写入不可变的运行上下文。
  * Agent 在其整个生命周期中必须仅使用此固化上下文。

### 4. THREE ASSURANCES / 三大保障
```
- DETERMINISM: The agent follows identical decision rules from start to finish.
- AUDITABILITY: The system proves to the merchant which policy version approved the refund.
- REPRODUCIBILITY: Engineers can replay the exact reasoning steps of the agent in a sandbox.
```
* **中文对照**：
  * 确定性：Agent 从头到尾遵循完全相同的决策规则。
  * 可审计性：系统向商户证明是哪一个策略版本批准了这笔退款。
  * 可复现性：工程师可以在沙箱中完全重放 Agent 当时的推理步骤。

### 5. MANDATORY INSTRUCTION / 强制指令
```
- Do not permit dynamic configuration updates on an active run.
- Apply all configuration updates only to newly created runs.
```
* **中文对照**：
  * 严禁对活跃的运行执行动态配置更新。
  * 所有配置更新必须仅应用于新创建的运行。

## 四、 工业级不可变上下文工程实现（Python + Pydantic v2）

```python
import hashlib
import json
from datetime import datetime, timezone
from typing import Any, Dict, List
from pydantic import BaseModel, Field, ConfigDict

class ModelSpec(BaseModel):
    model_config = ConfigDict(frozen=True)
    model_id: str
    temperature: float = 0.0
    seed: int = 42

class RiskPolicy(BaseModel):
    model_config = ConfigDict(frozen=True)
    max_auto_refund_limit: float
    allow_keep_item_threshold: float

class FrozenRunContext(BaseModel):
    """
    企业级不可变执行上下文 (Immutable Run Context)
    在 on_run_load 阶段创建后全局只读，严禁任何形式的动态篡改
    """
    model_config = ConfigDict(frozen=True)  # 严格不可变 (Frozen)

    run_id: str
    tenant_id: str
    config_snapshot_hash: str
    prompt_template_version: str
    model_spec: ModelSpec
    risk_policy: RiskPolicy
    tool_whitelist_hash: str
    frozen_at: datetime = Field(default_factory=lambda: datetime.now(timezone.utc))

    @classmethod
    def create_snapshot(
        cls,
        run_id: str,
        tenant_id: str,
        prompt_version: str,
        model_spec: ModelSpec,
        risk_policy: RiskPolicy,
        tools: List[str]
    ) -> "FrozenRunContext":
        # 计算白名单工具的单向哈希
        tool_hash = hashlib.sha256("::".join(sorted(tools)).encode("utf-8")).hexdigest()

        # 计算完整配置快照的内容指纹
        payload = {
            "prompt_version": prompt_version,
            "model_spec": model_spec.model_dump(),
            "risk_policy": risk_policy.model_dump(),
            "tool_hash": tool_hash
        }
        snapshot_hash = hashlib.sha256(json.dumps(payload, sort_keys=True).encode("utf-8")).hexdigest()

        return cls(
            run_id=run_id,
            tenant_id=tenant_id,
            config_snapshot_hash=snapshot_hash,
            prompt_template_version=prompt_version,
            model_spec=model_spec,
            risk_policy=risk_policy,
            tool_whitelist_hash=tool_hash
        )
```
