## 零、 核心全景对比：传统原地覆写 vs 企业级仅追加账本

在构建企业级 AI Agent 的受控宿主运行时（Harness）时，状态管理存在两种截然不同的架构路线：

```
【路线 A：传统玩具 Agent 原地覆写模式 (In-place Mutation)】- 致命缺陷！
Step 1 质检 ──► [覆写 status="INSPECTED"]
                       │
Step 2 运费 ───────────┴──► [原地抹除覆盖为 status="SHIPPING_CALCULATED"] (Step 1 历史彻底消失)
                                  │
Step 3 退款 ──────────────────────┴──► [原地抹除覆盖为 status="REFUNDED"] (车祸死无对证)

-----------------------------------------------------------------------------------------

【路线 B：企业级 Harness 事件溯源账本 (Append-Only Event Stream)】- 正统真理！
Step 1 质检 ──► [追加事件 E1: 磨损3处, 折旧15%, Hash=88a1f...] (永久封存，只读)
                       │
Step 2 运费 ───────────┼──► [追加事件 E2: 运费$35建议弃件, Hash=b4c2e...] (永久封存，只读)
                       │
Step 3 审批 ───────────┼──► [追加事件 E3: 主管审批通过退赔$50, 签名=#8821] (永久封存，只读)
                       │
Step 4 退款 ───────────┴──► [追加事件 E4: Stripe流水txn_3P已扣付, Hash=99f0a...] (永久封存，只读)
                                  │
                                  ▼ 动态折叠计算
                  【当前业务状态投影 (Materialized View)】
```

## 一、 传统玩具 Agent 的致命坏味道：原地覆盖修改（In-place Mutation）

很多开源玩具级 Agent 框架（如初学者的轻量 Python 脚本）习惯采用共享可变字典并在内存中原地覆写：

```python
# 致命坏味道：原地覆写变量！
run_state.current_tool_result = {"status": "SUCCESS", "step": 1}
# 下一步又覆盖掉了上一步：
run_state.current_tool_result = {"status": "FAILED", "step": 2} 
```

### 为什么这种写法在企业级生产环境中是灾难？
1. **历史不可追溯（审计抓瞎）**：  
   当发生资损或买家投诉时，工程师调出数据库，发现字段里只剩最后一次的报错。前面到底发生过什么？大模型在 Step 1 到底是怎么想的？调用了什么接口？全都像被“黑板擦”抹除了一样，死无对证。
2. **无法做时间旅行调试（Time-Travel Playback）**：  
   如果状态被覆盖，研发排查线上偶发 Bug 时，就只能看到**“车祸发生后的最终废墟”**，根本无法还原**“车子是怎么一步一步开进沟里的”**。
3. **并发写入的脑裂覆写**：  
   在分布式节点多线程/多协程并发推进时，原地更新极易诱发锁竞争、死锁，甚至因为读写交错引发脏写撕裂。

## 二、 企业级正统设计：微观绝对不可变，宏观仅追加（Append-Only Event Stream）

在 Harness 微内核中，真正的状态机不是一个“可以被随便改写的变量”，而是一本**“银行流水账本（Bank Ledger）”**！

### 1. 银行账务的核心铁律：
* 你去银行存了 100 块，银行记录一条流水：`+100`；
* 接着你取了 50 块，银行**绝不会在数据库里把上一行的 100 改成 50**，而是**追加记录一条新的流水**：`-50`；
* 你的当前账户余额，是由这串历史流水相加计算出来的**当前投影（Materialized View）**；
* 甚至如果你转账转错了，银行的操作也是**“追加一条冲正冲正记录（Compensation Entry）”**，绝对不会把原来的转账记录从数据库里物理擦除！

### 2. Agent 运行状态的真实物理全貌：
在我们的系统里，每一个 Step 产生的历史，都是**密封盖章后不可篡改的单向事件（Immutable Event）**：

```
┌────────────────────────────────────────────────────────────────────────┐
│              【历史事件链条：Append-Only Event Stream】                │
├────────────────────────────────────────────────────────────────────────┤
│ ▌Step 1 记录 (ID: event_01, 耗时 120ms) - 【已密封，永久只读】          │
│   * 动作：多模态质检 (multimodal_inspect)                              │
│   * 产出：识别出表带磨损 3 处，折旧率 15%                              │
│   * 防篡改哈希：sha256:88a1f...                                        │
├────────────────────────────────────────────────────────────────────────┤
│ ▌Step 2 记录 (ID: event_02, 耗时 340ms) - 【已密封，永久只读】          │
│   * 动作：逆向干线运费精算 (calc_shipping)                             │
│   * 产出：回国运费 $35，超出商品残值，建议仅退款                        │
│   * 防篡改哈希：sha256:b4c2e...                                        │
├────────────────────────────────────────────────────────────────────────┤
│ ▌Step 3 记录 (ID: event_03, 挂起 2 小时) - 【已密封，永久只读】         │
│   * 动作：人机协同审批 (human_approval)                                │
│   * 产出：主管飞书点击 APPROVED，批准赔付 $50                           │
│   * 审批人签名：Manager_David_Chen (工号 #8821)                        │
├────────────────────────────────────────────────────────────────────────┤
│ ▌Step 4 记录 (ID: event_04, 耗时 510ms) - 【刚刚追加写入】             │
│   * 动作：调用 Stripe 划款支付                                         │
│   * 产出：流水号 txn_3P... 已到账                                      │
│   * 防篡改哈希：sha256:99f0a...                                        │
└────────────────────────────────────────────────────────────────────────┘
```

## 三、 为什么说“Append-Only（生成了就不能改）”是企业级架构的灵魂？

结合我们的**跨境电商售后退赔 Agent（智能手表退赔 $50 案例）**，这种“生成即不可变”的设计带来了三大降维打击级的优势：

### 1. 终极防赖账与审计合规（Audit Trail & Anti-Tampering）
月末商户找平台扯皮：“*你们系统是不是事后改了数据？为什么给我独立站直接划走了 $50？*”  
* **有了 Append-Only**：系统直接导出该工单的**完整时间线账本**。每一条记录都包含前序步骤的哈希签名（Merkle 链）。任何黑客或内部人员哪怕在数据库里改动一个数字，整个哈希链条当场断裂报错。
* 这是一份**具备法律效力和司法鉴定效力的铁证**，消灭商户与平台之间的一切扯皮。

### 2. 秒级实现“时间旅行调试（Time-Travel Replay）”
线上出现了一笔诡异的决策，大模型为什么突然同意给一个明显骗货的买家退了款？  
* 研发人员想查原因，不需要繁琐地去复现现场。
* 因为历史记录是 Append-Only 的，研发人员可以命令测试沙箱：“**请将状态重放（Playback）到 Step 2 结束的那一刻！**”
* 系统直接读取第 1、第 2 条不可变事件，瞬间就能在本地内存中还原出模型在做出该决策前一毫秒的**所有心智状态与上下文截面**！

### 3. 故障接管时的“绝对幂等（Zero Double-Spend）”
如果节点在执行 Step 4（向银行划款）时突然遭遇硬件掉电宕机，备用节点被拉起唤醒。  
* 备用节点怎么知道打款到底执行了没有？
* 它翻阅不可变账本（`tool_ledger`）：
  * 如果账本里已经记录了 `stripe_refund` 的成功事件，**绝对严禁二次执行打款**！
  * 如果账本里记录的是 `UNKNOWN` 状态，立即转入对账状态机；
* **只有每一步都是永久不可篡改的日志，容灾恢复节点才能拥有绝对精确的“后视镜”！**

## 四、 架构层面的辩证统一：真正的“可变”是什么？

那么，我们常说的“可变状态”和“不可变”矛盾吗？一点都不矛盾！

在现代高级分布式理论中：
* **数据在物理存储上：是 100% 不可变的追加流水（Immutable Append-Only Log）**；
* **数据在程序表现上：是一个随着流水追加，不断被动态折叠计算出来的“最新投影（Current View / State Projection）”**。

```python
from datetime import datetime, timezone
from typing import List, Dict, Any, Optional
from pydantic import BaseModel, Field, ConfigDict


# ==============================================================================
# 微观：单步事件定义（一旦生成，严格只读）
# ==============================================================================
class StepEvent(BaseModel):
    """单步执行事件记录：一旦生成，严格封存，只读防篡改"""
    model_config = ConfigDict(frozen=True)  # ★ 核心：物理只读硬锁！

    event_id: str = Field(description="事件唯一ID，如 evt_01")
    step_index: int = Field(description="步数序号，如 1, 2, 3")
    action_type: str = Field(description="动作类型：THOUGHT / TOOL_CALL / HITL_APPROVAL")
    payload: Dict[str, Any] = Field(description="动作的入参、返回值与元数据")
    event_hash: str = Field(description="防篡改签名哈希")
    created_at: datetime = Field(default_factory=lambda: datetime.now(timezone.utc))


# ==============================================================================
# 宏观：状态账本（只增不改，通过只读属性动态折叠计算）
# ==============================================================================
class AppendOnlyRunState(BaseModel):
    """
    【宏观状态机】基于事件溯源的仅追加账本
    状态的推进只能通过 append_event()，绝对禁止原地覆盖旧事件！
    """
    run_id: str
    event_ledger: List[StepEvent] = []  # ★ 核心账本：只能 append，严禁修改已有条目

    def append_event(self, event: StepEvent) -> None:
        """只允许单调追加事件"""
        self.event_ledger.append(event)

    @property
    def current_step_count(self) -> int:
        """最新步数：由账本长度动态折叠得出"""
        return len(self.event_ledger)

    @property
    def total_refund_amount(self) -> float:
        """当前累计赔付金额：由不可变流水动态折叠累加计算"""
        total = 0.0
        for event in self.event_ledger:
            if event.action_type == "TOOL_CALL" and event.payload.get("tool_name") == "stripe_refund":
                total += event.payload.get("amount", 0.0)
        return total

    @property
    def is_human_approved(self) -> bool:
        """是否已获主管审批：扫描审批流水事件得出"""
        return any(
            e.action_type == "HITL_APPROVAL" and e.payload.get("decision") == "APPROVED"
            for e in self.event_ledger
        )
```

## 五、 核心设计总结卡

| 比较维度 | 传统覆写模式 (In-place Mutation) | Harness 仅追加模式 (Append-Only Event Stream) |
| :--- | :--- | :--- |
| **物理写入行为** | SQL `UPDATE state SET status = ...` | SQL `INSERT INTO step_events VALUES (...)` |
| **发生 Bug 时的现场** | 只能看到最后一步崩溃的“残骸” | 能 100% 复原出前序每一步的完整心智推导过程 |
| **事后责任审计** | 死无对证，商户指责平台篡改数据 | 完整加密哈希链，司法鉴定级不可推卸凭证 |
| **故障自愈能力** | 备用节点接管时不知道前序做了什么 | 备用节点清晰识别已提交动作，0 资损、0 重复划款 |
| **架构哲学** | 简单粗暴，玩具级脚本思维 | **银行账务级底座：覆写是原罪，追加是真理** |
