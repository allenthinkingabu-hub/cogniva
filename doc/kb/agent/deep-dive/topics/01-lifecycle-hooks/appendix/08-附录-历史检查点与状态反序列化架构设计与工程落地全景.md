## 零、 核心全景：Hook 7（存）与 Hook 1（取）的闭环协同拓扑

在企业级 AI Agent 的受控宿主运行时（Harness）中，检查点机制遵循 **“写时增量存盘，读时精确反水化（Rehydration）”** 的闭环设计，横跨 Ring 0（宿主物理态）与 Ring 3（模型认知态）：

```
                【写盘端：Hook 7 (before_checkpoint)】
                当前 Step 推理与工具执行完成，准备落盘
                             │
                             ▼
 ┌────────────────────────────────────────────────────────┐
 │ 1. 敏感凭据物理剥离 (脱敏密码、STS Token，绝不持久化)   │
 │ 2. 大对象分流 (状态 < 1MB 存 PG，> 1MB 异步转存 S3)   │
 │ 3. 单调递增 Fencing Token 并通过 CAS 乐观锁落盘         │
 └───────────────────────────┬────────────────────────────┘
                             │
                             ▼ (写入持久化存储: run_checkpoints)
                   [(PostgreSQL JSONB + S3 Blob)]
                             │
                             ▼ (断点续跑唤醒 / 节点宕机备用节点接盘)
                【加载端：Hook 1 (on_run_load)】
                             │
 ┌───────────────────────────┴────────────────────────────┐
 │ 1. 抢占 Redis 30s 租约，确认当前为唯一 Master         │
 │ 2. 查阅最新 Checkpoint (ORDER BY fencing_token DESC)   │
 │ 3. 内存反水化：还原思维链、工具调用账本、业务状态机     │
 │ 4. 重新注入不可变上下文 (FrozenRunContext)，放行后续   │
 └────────────────────────────────────────────────────────┘
```

## 一、 企业级技术栈选型与权衡矩阵

| 组件层级 | 推荐选型 | 为什么这样选？（工程权衡） | 备选方案 |
| :--- | :--- | :--- | :--- |
| **序列化引擎** | **Pydantic v2 (Rust 内核) + Msgpack** | 比标准 Python JSON 序列化**快 15~20 倍**；反序列化具备严格类型校验（Strict Typing），杜绝非法状态污染。 | Protobuf、FastJSON |
| **主状态存储** | **PostgreSQL (JSONB + GIN 索引)** | 天然支持 SQL 级原子 CAS 锁（`WHERE fencing_token = :token`）；支持针对 JSONB 内部特定字段建立索引，方便按工单查询。 | MySQL 8.0, CockroachDB |
| **大对象分流** | **MinIO / AWS S3** | 当 Agent 分析海量 PDF、多模态高分辨率图像时，上下文可能膨胀到 20MB。**大对象禁止直接塞入数据库行**，存 S3 并以 URL 指针入库。 | Ceph, GCS |
| **租约与心跳** | **Redis Cluster (Lua 脚本原子操作)** | 亚毫秒级读写，天然具备 TTL 过期机制，消灭锁死。 | etcd, Consul |

## 二、 工业级 Checkpoint 核心数据模型设计

企业级检查点绝不能简单存一个 `raw_json`，它必须承载 **“工具防重执行账本、单调版本号、审计签名”**：

### 1. PostgreSQL 表结构设计 (`run_checkpoints`)
```sql
CREATE TABLE run_checkpoints (
    checkpoint_id     UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    run_id            VARCHAR(64) NOT NULL,
    tenant_id         VARCHAR(64) NOT NULL,
    step_index        INT NOT NULL,                  -- 当前执行到第几步 (0, 1, 2...)
    fencing_token     BIGINT NOT NULL,               -- 单调递增隔离令牌 (防脑裂核心)
    checkpoint_type   VARCHAR(32) NOT NULL,          -- STEP_COMMITTED | SUSPENDED_HITL | ERROR_HOLD
    
    -- 核心状态载荷 (核心元数据存 JSONB，超限大对象存指针)
    thought_history   JSONB NOT NULL,                -- 完整的 ReAct 思维链上下文快照
    tool_call_ledger  JSONB NOT NULL,                -- 【核心】工具调用防重账本 (已执行结果)
    business_state    JSONB NOT NULL,                -- 业务状态机当前快照 (如 DISPUTE_AUDITED)
    
    -- 大对象分流指针
    blob_payload_url  TEXT DEFAULT NULL,             -- 若上下文 > 1MB，存 S3 外部对象存储路径
    
    -- 审计与数据完整性
    merkle_step_hash  CHAR(64) NOT NULL,             -- 当前步骤的 Merkle Hash，防事后篡改
    created_at        TIMESTAMP WITH TIME ZONE DEFAULT NOW(),
    
    -- 联合唯一索引：保障一个 Run 的一个步骤只能有一条最终版本
    CONSTRAINT uk_run_step_token UNIQUE (run_id, step_index, fencing_token)
);

CREATE INDEX idx_run_checkpoints_lookup ON run_checkpoints (run_id, fencing_token DESC);
```

### 2. 工具调用防重账本（`tool_call_ledger`）的内部结构
这是防止“断点续跑后向买家重复退款”的最关键数据结构：
```json

    }
  ]
}
```

## 三、 状态反序列化流水线：5 步硬核水化（Rehydration）机制

当一个全新的 Worker 节点在 `on_run_load` 被唤醒，试图接管或续跑一个工单时，Harness 执行以下 **5 步原子操作**：

```
[Worker 接单] ──► 1. 查最新检查点 ──► 2. 内存反序列化 ──► 3. 密钥按需重签
                      │
                      ▼
              4. 重建工具账本 ──► 5. 封装置入不可变上下文 ──► [放行进入 Hook 2]
```

### 1. 第一步：获取最新且唯一的权威检查点快照
Worker 执行 SQL，以递增的 `fencing_token` 降序排列，取最新一条：
```sql
SELECT step_index, fencing_token, checkpoint_type, thought_history, tool_call_ledger, business_state, blob_payload_url
FROM run_checkpoints
WHERE run_id = :run_id
ORDER BY fencing_token DESC
LIMIT 1;
```
* **若记录为空**：说明是全新创建的任务（Fresh Run），初始化空的 `step_index = 0, fencing_token = 1`。
* **若记录存在**：解析出该任务已被推进到了第几步。

### 2. 第二步：分流拉取与强类型 Pydantic 内存还原
* 检查 `blob_payload_url` 是否有值。若有，并发向 S3 发起 `GetObject`，拉取大模态原始数据；
* 调用 Pydantic v2 模型，执行反序列化验证：
  ```python
  # 使用 Rust 内核完成纳秒级强类型转换，若被篡改则立即抛出 StateCorruptionException
  rehydrated_state = AgentInternalState.model_validate_json(raw_checkpoint_data)
  ```

### 3. 第三步：安全隔离——敏感凭证“禁止落盘，运行时重签（Secret Re-hydration）”
* **企业级高危红线**：数据库检查点里**严禁持久化商户 API Key、银行 STS Token 或内部密钥**，否则一旦数据库泄露将引发灾难。
* **解决方案**：检查点只存业务逻辑数据。在 Rehydrate 阶段，由 Harness 内核拿着当前的 `tenant_id`，向企业密钥中心（KMS / Vault）动态换取一个 **60 秒有效期的临时短期 STS Token**，重新绑定到内存上下文中。

### 4. 第四步：激活“工具防重账本（Tool Ledger Mock Hook）”
* Worker 将 `tool_call_ledger` 注入宿主执行器（Harness Executor）；
* **关键拦截**：当大模型恢复推理时，如果大模型再次提出想要执行 `issue_retention_coupon`（发优惠券），Harness 的 Hook 5（`before_action`）会**直接拦截并命中账本**：
  * “系统发现该工具在历史 Checkpoint 中已经执行过了（匹配到唯一 `operation_ref`）！”
  * Harness **直接从账本中取回上次的结果返回给模型，绝不发生真实的二次网络外呼**！

### 5. 第五步：装配不可变的 `FrozenRunContext` 并递增版本
* 将还原好的所有数据，封装进一个只读对象（`FrozenRunContext`）；
* 将全局隔离版本号递增：`new_fencing_token = fencing_token + 1`，并将状态标记为活跃，放行进入 Hook 2（`before_context`）。

## 四、 核心代码落地骨架（Python + Pydantic v2 生产级示范）

```python
from typing import Dict, Any, List, Optional
from pydantic import BaseModel, Field
import json

class ToolLedgerEntry(BaseModel):
    call_id: str
    tool_name: str
    operation_ref: str
    status: str  # COMMITTED | UNKNOWN | FAILED
    result: Dict[str, Any]

class RehydratedAgentState(BaseModel):
    run_id: str
    tenant_id: str
    step_index: int
    fencing_token: int
    thought_history: List[Dict[str, str]]
    tool_ledger: List[ToolLedgerEntry]
    business_state: Dict[str, Any]

class CheckpointRehydrationService:
    def __init__(self, db_pool, kms_client, s3_client):
        self.db = db_pool
        self.kms = kms_client
        self.s3 = s3_client

    async def rehydrate_run(self, run_id: str, current_tenant_id: str) -> RehydratedAgentState:
        # 1. 查询数据库最新持久化检查点
        sql = """
            SELECT step_index, fencing_token, checkpoint_type, thought_history, 
                   tool_call_ledger, business_state, blob_payload_url
            FROM run_checkpoints
            WHERE run_id = $1 AND tenant_id = $2
            ORDER BY fencing_token DESC LIMIT 1;
        """
        row = await self.db.fetchrow(sql, run_id, current_tenant_id)
        
        # 2. 如果是新任务，执行全新实例化
        if not row:
            return RehydratedAgentState(
                run_id=run_id,
                tenant_id=current_tenant_id,
                step_index=0,
                fencing_token=1,
                thought_history=[],
                tool_ledger=[],
                business_state={"status": "INITIALIZED"}
            )

        # 3. 如果有大对象，从 S3 拉取合并
        thought_data = row["thought_history"]
        if row["blob_payload_url"]:
            blob_content = await self.s3.get_object(row["blob_payload_url"])
            thought_data["large_context"] = blob_content

        # 4. Pydantic v2 严格反序列化水化回内存模型
        state = RehydratedAgentState(
            run_id=run_id,
            tenant_id=current_tenant_id,
            step_index=row["step_index"],
            fencing_token=row["fencing_token"] + 1,  # 增量自增，防止脑裂
            thought_history=thought_data,
            tool_ledger=[ToolLedgerEntry(**item) for item in row["tool_call_ledger"]],
            business_state=row["business_state"]
        )
        
        return state
```

## 五、 生产级防御三大核心业务价值

1. **防资金重刷（Zero-Double-Spend）**：借助反水化出来的 `tool_ledger`，已产生物理副作用的外部接口绝不会因为服务重启被调用第二次。
2. **防脑裂脏写（Zero-Split-Brain）**：每次 Rehydration 必定让 `fencing_token` 自增，假死唤醒的老 Worker 执行写操作时必然被数据库 CAS 阻断自杀。
3. **低存储成本与高吞吐（High-Performance Storage）**：小元数据走 PostgreSQL JSONB，大上下文走 S3，反序列化基于 Rust 原生内核，单次状态恢复在 **5 毫秒以内** 完成。
