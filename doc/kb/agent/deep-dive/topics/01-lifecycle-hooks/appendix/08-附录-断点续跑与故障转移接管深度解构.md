在企业级 AI Agent 架构与分布式系统工程中，**“断点续跑（Resume Run）”** 与 **“节点故障转移接管（Failover Recovery）”** 是两个看似相似、但**触发诱因、安全风险和处理逻辑完全不同**的核心容灾机制。

它们是为什么我们必须在 `on_run_load` 中执行“历史检查点反序列化（State Rehydration）”的根本原因。

---

## 一、 核心本质区别一览（结论先行）

| 比较维度 | **断点续跑 (Resume Run)** | **节点故障转移接管 (Failover Recovery)** |
| :--- | :--- | :--- |
| **触发性质** | **“预期内的计划中挂起”**（业务与流程驱动） | **“非预期的灾难性宕机”**（基础设施与硬件驱动） |
| **典型触发场景** | * 人机协同审批（Human-in-the-Loop）：退款超限等待主管批准<br>* 长周期异步回调：等待海外仓库 2 小时后回传质检结果<br>* 算力配额耗尽：主动挂起等待次日配额刷新 | * Worker 节点物理机断电、硬件损坏<br>* 进程内存打满被 K8s 暴力 OOM-Killed (`kill -9`)<br>* 宿主节点网络被拔线（底层网络分区） |
| **状态持有者** | 前序 Worker 已**安全释放资源并主动持久化**落盘。 | 前序 Worker **突然猝死**，内存上下文全部灰飞烟灭。 |
| **核心挑战** | **“如何无损还原上下文，杜绝重复从第 1 步盲跑”** | **“如何确认前任已死，防止脑裂并安全接盘”** |

## 二、 深入剖析场景一：断点续跑（Resume Run）

### 1. 为什么 AI Agent 极度依赖断点续跑？（不可逆副作用与 Token 成本）
传统 Web 接口如果中断，客户端通常“重试一次”即可。但 AI Agent **绝对不能从头重试**：
1. **物理副作用不可逆**：假设一个退赔 Agent 总共需要 4 步：
   * Step 1：调用物流接口核验包裹（只读）
   * Step 2：向买家发放一张 $10 优惠券作为安抚（**物理写操作，已入账！**）
   * Step 3：向买家退款 $40（因为金额大，系统触发风控，转入**人工审核**挂起）
   * Step 4：向买家发送确认邮件
   * **灾难后果**：如果主管在 3 小时后审批通过，Agent 却从 Step 1 重新从头跑，买家就会**再收到一张 $10 优惠券**！造成直接资金资损。
2. **算力成本巨大**：复杂 Agent 往往已经经历了数轮 ReAct 思考，积累了数万 Token 上下文。如果中途挂起后再重新从头推理，将白白消耗几美金的 Token 算力。

### 2. 断点续跑的完整流转过程
```
[Step 2 执行完] ──► 触发风控: 需人工审批 ──► Harness 调用 Hook 7 (before_checkpoint)
                                                │
                                                ▼ (落盘保存 Checkpoint #2)
                                   [任务进入 SUSPENDED 挂起态，Worker 优雅退出]
                                                │
                                    (3小时后，主管在后台点击“审批通过”)
                                                │
                                                ▼ (调度网关重新唤起任务)
                                   [Worker-B 执行 Hook 1: on_run_load]
                                                │
                                                ▼ (状态反序列化)
              从 DB 读取 Checkpoint #2 ──► 恢复记忆上下文、已发券记录与 Step 计数器
                                                │
                                                ▼ (无缝接力)
                                   [直接进入 Step 3 执行打款，绝不重跑 Step 1 & 2]
```

## 三、 深入剖析场景二：节点故障转移接管（Failover Recovery）

### 1. 故障现场：前任节点“突然暴毙”
在分布式 K8s 集群中，服务随时可能发生非正常死亡：
* **车祸瞬间**：Worker-A 正在给手表工单 `dispute_999` 推理退款决策，由于相邻容器突发内存溢出，K8s 节点触发驱逐机制，**直接向 Worker-A 发送 `SIGKILL` 强杀容器**。
* **致命问题**：
  * Worker-A 根本来不及执行任何 `finally` 代码块；
  * Worker-A 内存里的所有变量全部丢失；
  * 工单 `dispute_999` 悬挂在半空中，没人管了。

### 2. 故障自愈的四步接盘闭环（Failover Takeover）

这时，`on_run_load` 配合分布式租约，展现出无人值守自愈的威力：

```
                      【Worker-A 突然猝死 (OOM / 硬件断电)】
                                       │
                                       ▼ (致命静默)
             [Worker-A 的心跳守护线程死亡，不再向 Redis 续租]
                                       │
                                       ▼ (时间流逝 30 秒)
                [Redis 30s 租约自动到期消亡: run:lease:dispute_999]
                                       │
                                       ▼ (故障感知)
              [备用节点 Worker-B 发现任务悬挂，尝试接管调度]
                                       │
 ┌─────────────────────────────────────┴─────────────────────────────────────┐
 │                 【Worker-B 执行 Hook 1: on_run_load 接盘流水线】            │
 │                                                                           │
 │  第一步 (抢占新租约) : 执行 SET run:lease:dispute_999 Worker-B NX EX 30    │
 │                        成功抢占！Worker-B 成为该工单的法定新 Master。     │
 │                                                                           │
 │  第二步 (核查墓碑标记) : 访问只读 DB，确认任务在此期间没有被买家取消。    │
 │                                                                           │
 │  第三步 (检查点反序列化): 从数据库查询该任务【最后一次成功落盘的快照】:   │
 │                         SELECT * FROM run_checkpoints                     │
 │                         WHERE run_id = 'dispute_999'                      │
 │                         ORDER BY fencing_token DESC LIMIT 1;              │
 │                                                                           │
 │  第四步 (状态回放与隔离): 还原 Step 状态与内存记忆；将 fencing_token 自增，│
 │                         彻底在存储层防范 Worker-A 假死苏醒后的脏写。      │
 └─────────────────────────────────────┬─────────────────────────────────────┘
                                       │
                                       ▼
                  [Worker-B 从最近的确定性状态继续安全推进]
                  (买家感知不到后台发生过宕机，系统实现高可用自愈)
```

## 四、 底层基石：历史检查点（Checkpoint）到底装了什么？

无论断点续跑还是故障转移，其能够“无缝接盘”的前提，是数据库中的 `run_checkpoints` 必须记录足够完备的**上下文快照**：

```sql
SELECT 
    step_count,          -- 当前执行到了第几步 (如 Step 3)
    fencing_token,       -- 单调递增隔离令牌 (防脑裂版本号)
    memory_snapshot,     -- Agent 的思维链、变量、用户初始输入与反思历史
    execution_state,     -- 业务状态机所处的阶段 (如 DISPUTE_AUDITED)
    last_tool_results    -- 已经执行完成的工具返回数据 (如发券成功记录，无需重调)
FROM run_checkpoints 
WHERE run_id = :run_id 
ORDER BY fencing_token DESC LIMIT 1;
```

## 总结对照

* **断点续跑（Resume Run）**：解决的是长周期 Agent 的**“业务持久度”**问题——允许任务睡过去（等待人或外部事件），睡醒后在任意节点**精准接力**，不白花钱、不产生重复副作用。
* **节点故障转移（Failover Recovery）**：解决的是分布式集群的**“系统高可用”**问题——允许节点突然死掉，备用节点能在 30 秒内**自动夺权并复活任务**，保障企业级服务永远不卡死、不停摆。
