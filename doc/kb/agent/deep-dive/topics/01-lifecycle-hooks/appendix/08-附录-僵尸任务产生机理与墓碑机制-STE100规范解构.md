## 零、 异步排队与状态竞争时序流（Chronological Flow）

```
[Time T0] 用户提交售后争议退款工单 (Dispute Case #999)
          - 调度网关向消息队列 (Kafka) 写入事件 E1
          - 队列处于流量高峰期，事件 E1 在延迟队列中排队等待
                         │
                         ▼
[Time T1] 用户在前端改变主意，点击“撤销维权申请”
          - 业务服务直接修改数据库：is_cancelled = true (挂载墓碑)
          - 数据库更新瞬间完成
          - 但 Kafka 分区日志不可变，无法直接从中拔除排队中的 E1
                         │
                         ▼
[Time T2] Worker 节点空闲，从 Kafka 队列中拉取到旧事件 E1
          │
          ├────────────────────────────────┬────────────────────────────────┐
          ▼ (传统裸跑 Agent: 无墓碑核查)   ▼ (落地 Harness 门禁: 墓碑核查)
   [ 唤醒大模型推理并向银行退款 $50 ]     [ 优先查询只读 DB: is_cancelled = true ]
   [ 僵尸任务复活，引发严重双重资损 ]     [ 当场物理熔断自杀，0 Token，0 资损 ]
```

## 一、 DEFINITION / 概念定义

### STE English:
1. A Zombie Run is a background execution of an aborted task.
2. The business object was already cancelled or deleted by a user.
3. But a worker still executes the task and calls external services.
4. The worker processes stale event data.

### 标准中文对照：
1. 僵尸任务（Zombie Run）是指对一个已被中止任务的后台执行。
2. 对应的业务对象已被用户主动取消或删除。
3. 但工作节点仍然执行该任务并调用外部系统。
4. 工作节点处理的是陈旧的过期事件数据。

## 二、 ROOT CAUSES: HOW A ZOMBIE RUN OCCURS / 僵尸任务产生的完整时序机理

### STE English:
1. **Step 1: Asynchronous Message Queue Delay**:
   * A user submits a dispute refund request at Time T0.
   * The system writes an event message to Kafka.
   * The queue has traffic congestion.
   * The event message waits in the queue for 10 seconds.

2. **Step 2: Out-Of-Band Cancellation**:
   * At Time T1, the user changes their mind.
   * The user clicks "Cancel Request" on the web page.
   * The web service updates the database record to `is_cancelled = true`.
   * The database operation finishes immediately.

3. **Step 3: Message Immutability in Message Brokers**:
   * Distributed message brokers (like Kafka) use append-only logs.
   * A producer cannot modify or delete a single message inside a partition log.
   * Therefore, the original event message remains in the queue.

4. **Step 4: Worker Pick-up and Zombie Awakening**:
   * At Time T2, a worker becomes free and reads the event message.
   * The payload inside the message still says: "Process Refund".
   * The worker does not inspect the current database state.
   * The worker calls the LLM and the bank payment API.
   * The system sends money to a cancelled dispute.
   * This invalid execution is a **Zombie Run**.

### 标准中文对照：
1. **步骤 1：异步消息队列排队延迟**：
   * 用户在时间 T0 提交售后退款申请。
   * 系统向 Kafka 写入一条事件消息。
   * 队列存在流量积压。
   * 该事件消息在队列中等待排队 10 秒。

2. **步骤 2：带外撤单（业务状态先行变更）**：
   * 在时间 T1，用户改变主意。
   * 用户在前端网页点击“撤回申请”。
   * 网页服务直接将数据库记录更新为 `is_cancelled = true`。
   * 数据库更新瞬间完成。

3. **步骤 3：消息队列的不可变日志特性**：
   * 分布式消息队列（如 Kafka）采用只追加写日志（Append-only log）。
   * 生产者无法在分区日志中间单独修改或删除单条排队中的消息。
   * 因此，原有的退款事件消息依然留在队列中排队。

4. **步骤 4：工作节点拾取与僵尸唤醒**：
   * 在时间 T2，某个工作节点空闲并拉取到该事件消息。
   * 消息体内部的数据依然写着：“执行退款”。
   * 若工作节点不检查数据库最新状态，便直接执行。
   * 工作节点唤醒大模型并调用银行支付接口。
   * 系统向一个已被撤销的工单错误划扣退款。
   * 这次无效的执行就是**僵尸任务（Zombie Run）**。

## 四、 HOW TOMBSTONE VERIFICATION PREVENTS IT / 墓碑核查如何消灭僵尸任务

### STE English:
1. The database record with `is_cancelled = true` is a **Tombstone**.
2. A tombstone marks a resource as dead without physical deletion.
3. The worker acquires the 30-second lease first.
4. The worker reads the tombstone status from the database before calling the LLM:
   ```sql
   SELECT is_cancelled, tombstone_marked_at, cancel_reason 
   FROM order_dispute_cases 
   WHERE dispute_id = :dispute_id;
   ```
5. If `is_cancelled` is true, the worker aborts execution immediately.
6. The worker deletes the lease and logs `ABORTED_BY_TOMBSTONE`.
7. The system uses zero LLM tokens and makes zero bank payments.

### 标准中文对照：
1. 数据库中带有 `is_cancelled = true` 标记的记录被称为**墓碑（Tombstone）**。
2. 墓碑标记某个资源已死亡，但暂不执行物理删除。
3. 工作节点首先获取 30 秒分布式租约。
4. 工作节点在调用大模型之前，必须先从数据库读取该墓碑状态：
   ```sql
   SELECT is_cancelled, tombstone_marked_at, cancel_reason 
   FROM order_dispute_cases 
   WHERE dispute_id = :dispute_id;
   ```
5. 若 `is_cancelled` 为真，工作节点立即中止执行。
6. 工作节点删除租约，并记录审计日志 `ABORTED_BY_TOMBSTONE`。
7. 系统消耗 0 个模型 Token，并且产生 0 笔银行付款。
