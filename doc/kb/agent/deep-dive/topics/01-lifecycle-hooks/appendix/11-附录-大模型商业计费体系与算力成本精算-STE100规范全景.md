## 第一章：ASD-STE100 国际技术标准规范（Technical Specification）

> 本章遵循 **ASD-STE100（简明英语标准，Simplified Technical English）** 国际规范编写。  
> 规范要求：句子长度严格控制在 20 词以内，每句仅表达单一技术指令或判定，动词采用主动语态，严禁使用模棱两可与情绪化词汇。

### 1. PURPOSE AND DEFINITION (目的与定义)
* The Harness monitors large language model financial costs.
* Model providers bill by tokens, not by network requests.
* Tokens have different prices for input, output, and caching.
* The system must calculate accurate costs for each execution.
* The Harness must optimize token usage to protect profit margins.

### 2. SYSTEM INVARIANTS (系统不变量)
* **Rule 1**: Output token price must be calculated at the correct multiplier (three to four times).
* **Rule 2**: System prompts must be cached to reduce input costs.
* **Rule 3**: The maximum cost per ticket must not exceed the approved limit ($0.30 USD).
* **Rule 4**: Image tokens must be calculated from tile dimensions before model invocation.

### 3. PROCEDURE (标准执行程序)
* **Step 1**: Count input tokens and image tiles in Hook 2 before model call.
* **Step 2**: Apply prompt caching flags to static policy sections.
* **Step 3**: Estimate the maximum output token count for the task phase.
* **Step 4**: Compute the total estimated cost using the model pricing table.
* **Step 5**: Deduct the estimated budget in Hook 3 before network transmission.
* **Step 6**: Settle the final cost in Hook 4 using the actual returned token usage.

### 4. WARNINGS AND PROHIBITIONS (警告与操作禁忌)
* **WARNING**: Do not estimate cost using input token counts alone.
* **PROHIBITION**: Do not permit unrestricted output token generation.
* **PROHIBITION**: Do not duplicate uncached static policy text across multiple steps.
* **PROHIBITION**: Do not use production real-time endpoints for non-urgent offline batch tasks.

## 第二章：大模型商业计费底层机理（为什么输出比输入贵 3~4 倍？）

许多初涉 AI Agent 的工程师会产生直觉误区：“既然大模型处理的是文本，为什么输入 1,000 字和输出 1,000 字的价格天差地别？”

商业大模型计费的**非对称性（Asymmetric Pricing）**不是商业噱头，而是由现代 GPU 硬件微架构与 Transformer 计算范式决定的物理必然：

```
┌────────────────────────────────────────────────────────────────────────────────────────┐
│                              输入计算阶段 (Prefill Phase)                              │
│  • 计算特征: 并行矩阵乘法 (GEMM)                • 硬件瓶颈: 计算密集型 (Compute Bound)   │
│  • 机制: 一次性将上下文 N 个 Tokens 喂入 GPU     • GPU 利用率: 接近 100% Tensor Core 满载 │
│  • 计费结果: 算力吞吐极其高效，单位成本极低 (例如 $2.50 / 1M Tokens)                    │
└────────────────────────────────────────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────────────────────────────────────────┐
│                            输出生成阶段 (Decoding Phase)                               │
│  • 计算特征: 自回归串行生成 (Autoregressive)    • 硬件瓶颈: 访存带宽密集型 (Memory Bound) │
│  • 机制: 逐字生成，每产出 1 个 Token 必须把庞大   • GPU 利用率: 算力空转，受限于显存读取    │
│          KV Cache 与几百 GB 权重重新搬运一次                                            │
│  • 计费结果: 硬件效率断崖式下跌，单价昂贵 3 ~ 4 倍 (例如 $10.00 ~ $15.00 / 1M Tokens)     │
└────────────────────────────────────────────────────────────────────────────────────────┘
```

### 2.1 Prefill 并行矩阵乘 vs Decoding 显存带宽受限

1. **输入阶段（Prompt Evaluation / Prefill）——计算密集型（Compute-Bound）**：
   * 用户发送 10,000 Tokens 的上下文，GPU 将这 10,000 个 Tokens 打包为稠密矩阵（Matrix Batch）；
   * 通过多头自注意力机制（Self-Attention）一次性完成并行前向传播；
   * GPU 的 Tensor Core 算力利用率高达 90%+，计算吞吐量极高，能耗与时间被均摊。因此，**输入 Token 价格极度亲民**。
2. **输出阶段（Token Generation / Decoding）——内存带宽受限（Memory-Bound）**：
   * 大模型本质是**马尔可夫链式自回归模型**：生成第 $T+1$ 个 Token，必须依赖前 $T$ 个已生成 Token 的概率分布，**无法并行计算**！
   * 每蹦出 1 个 Token，GPU 都必须从 HBM 显存（High Bandwidth Memory）中将全模型的几百 GB 权重参数以及积累的巨大 KV Cache 读取一遍；
   * 现代 GPU 的计算速度远超显存搬运速度，GPU 计算单元大量时间在“等显存数据”，物理效率极度低下。因此，**厂商必须向输出 Token 索取 3~4 倍以上的高额溢价**以补偿 GPU 资源的隐形占满。

## 第三章：大模型降本四大核心武器

在 AI Agent 架构体系中，如果架构师只懂得“写 Prompt”，算力账单会迅速失控。掌握大模型四大原生降本特性，是微内核设计的基本功：

```
                             ┌───────────────────────────────────────────────┐
                             │       AI Agent 企业级算力降本四大武器          │
                             └───────────────────────┬───────────────────────┘
                                                     │
         ┌───────────────────┬───────────────────────┼───────────────────────┬───────────────────┐
         ▼                   ▼                       ▼                       ▼                   ▼
【1. Prompt Caching】   【2. Batch API】        【3. 视觉分片压降】     【4. PTU 预留实例】
静态政策命中打 1 折     离线非实时打 5 折       图像自适应降采样分辨率   包月固定算力封顶
```

### 3.1 Prompt Caching（上下文缓存——Agent 降本最高杠杆）
* **原理**：Agent 每一轮对话中，系统提示词（System Prompt）、法律条文、工具函数描述（JSON Schema）通常占据数千 Tokens 且保持恒定。Prompt Caching 在云端将这部分前缀文本的 KV Cache 驻留在 GPU 显存内（通常 5 分钟 TTL，每次命中自动刷新）；
* **经济效益**：后续轮次命中缓存后，不仅 Prefill 延迟降低 80%，**计费直接降至 1 折 ~ 2.5 折**；
* **落地铁律**：**固定前缀不可变！** 动态变化的数据（如买家最新一句话、时间戳）必须严格放在 Prompt 尾部，严禁插入在头部导致缓存失效（Cache Miss）。

### 3.2 Batch API（异步批处理 50% 折扣）
* **原理**：非实时工单（例如：客服历史质检、每日赔付对账、离线生成合规审计摘要），通过专用 Batch 端点提交，由供应商在算力低谷期（通常 24 小时内）调度执行；
* **经济效益**：输入和输出价格**全线直接减半（50% 硬折扣）**。

### 3.3 多模态切片计费优化（Vision Tile Optimization）
* **原理**：大模型处理破损图片时，按固定像素瓦片（如 $512 \times 512$）切片计费。一张 $2048 \times 2048$ 的大图会被切成 16 个 Tiles，产生超过 2,800 个 Tokens；
* **降本动作**：在 Hook 2（`before_context`）中由本地图像轻量预处理器执行自适应缩放（Downsampling），控制在单 Tile 范围（约 765 Tokens），瞬间节省 70% 图片算力费用。

### 3.4 专属预留吞吐（Provisioned Throughput Units / PTU）
* **原理**：超大规模企业（如大型跨境电商平台）向微软 Azure 或 AWS 采购独占 GPU 算力卡槽；
* **经济效益**：按月/年支付固定租金（几十万美元），在租用算力范围内**不再按 Token 计量扣费**，从根本上杜绝突发流量导致的弹性账单暴雷。

## 第四章：跨境电商售后退赔 Agent 真实工单财务精算实录

我们以法国巴黎买家 Alice 购买 $180 智能手表表盘划痕争议理赔工单 `ORD-20261104-8839` 为例，使用顶级模型 `Claude 3.5 Sonnet` 进行端到端精确财务核算。

### 4.1 单笔工单处理时序与 Token 消耗流水

该工单在 Harness 控制环中经历 3 轮推演：
* **Step 1（初审与意图识别）**：加载官方退赔政策模板（4,000 Tokens）+ Alice 留言与订单信息（1,000 Tokens）+ 手表破损图片（800 Tokens） $\rightarrow$ 规划调用视觉质检 API；
* **Step 2（事实核验与逆向物流查询）**：前置上下文 + 质检返回报告 + 调用 TMS 物流系统查询运费（新增 1,450 Tokens） $\rightarrow$ 规划运费与折价补偿比对；
* **Step 3（终审决策与仲裁书输出）**：全部事实聚合（新增 1,550 Tokens） $\rightarrow$ 输出最终赔付方案（仅退款 $54）与多语言用户解释信。

---

### 4.2 两种模式的财务账本残酷对比

#### 模式 A：无任何工程优化的“裸奔模式”
* **Step 1**：
  * 输入：$5,800 \text{ tokens} \times \frac{\$3.00}{10^6} = \$0.0174$
  * 输出：$250 \text{ tokens} \times \frac{\$15.00}{10^6} = \$0.00375$
* **Step 2**（上下文全量累加）：
  * 输入：$7,500 \text{ tokens} \times \frac{\$3.00}{10^6} = \$0.0225$
  * 输出：$350 \text{ tokens} \times \frac{\$15.00}{10^6} = \$0.00525$
* **Step 3**（上下文全量累加）：
  * 输入：$9,400 \text{ tokens} \times \frac{\$3.00}{10^6} = \$0.0282$
  * 输出：$600 \text{ tokens} \times \frac{\$15.00}{10^6} = \$0.0090$
* 💰 **单单总成本**：  
  $$\text{Cost}_{raw} = \$0.0174 + \$0.00375 + \$0.0225 + \$0.00525 + \$0.0282 + \$0.0090 = \mathbf{\$0.0861 \text{ 美元}}$$
  *(折合人民币约 0.62 元 / 单)*

#### 模式 B：Harness 微内核优化模式（Prompt Caching + 输出动态硬夹持）
* **优化策略**：
  1. 在 Hook 2 将 4,000 Tokens 静态政策模具打上 Cache 标记，Step 2 与 Step 3 享受 **$0.30/1M（1折）** 费率；
  2. 在 Hook 3 对输出长度动态夹持，消除冗余废话，Step 1 输出压至 150 tokens，Step 2 压至 200 tokens，Step 3 压至 400 tokens。
* **Step 1**：
  * 输入：\$0.0174（首次写入缓存）
  * 输出：$150 \text{ tokens} \times \frac{\$15.00}{10^6} = \$0.00225$
* **Step 2**：
  * 缓存命中输入：$4,000 \text{ tokens} \times \frac{\$0.30}{10^6} = \$0.0012$
  * 增量输入：$3,350 \text{ tokens} \times \frac{\$3.00}{10^6} = \$0.01005$
  * 输出：$200 \text{ tokens} \times \frac{\$15.00}{10^6} = \$0.0030$
* **Step 3**：
  * 缓存命中输入：$4,000 \text{ tokens} \times \frac{\$0.30}{10^6} = \$0.0012$
  * 增量输入：$4,950 \text{ tokens} \times \frac{\$3.00}{10^6} = \$0.01485$
  * 输出：$400 \text{ tokens} \times \frac{\$15.00}{10^6} = \$0.0060$
* 💰 **单单总成本（优化后）**：  
  $$\text{Cost}_{opt} = \$0.0174 + \$0.00225 + \$0.0012 + \$0.01005 + \$0.0030 + \$0.0012 + \$0.01485 + \$0.0060 = \mathbf{\$0.04595 \text{ 美元}}$$
  *(折合人民币约 0.33 元 / 单)*

## 第五章：Java 21 生产级算力计量与成本核算引擎 (`ModelBillingCalculator.java`)

以下为在受控宿主运行时中落地的工业级 Token 账本精算器：

```java
package com.cogniva.agent.harness.billing;

import java.math.BigDecimal;
import java.math.RoundingMode;
import java.util.Objects;

/**
 * Hook 4 商业大模型综合计费核算引擎
 * 支持输入、输出、Prompt Caching 命中、视觉切片等多维成本精确计算
 */
public final class ModelBillingCalculator {

    private static final BigDecimal ONE_MILLION = new BigDecimal("1000000");

    public record ModelPricingSchedule(
            String modelId,
            BigDecimal pricePerMillionInputUsd,
            BigDecimal pricePerMillionCachedInputUsd,
            BigDecimal pricePerMillionOutputUsd
    ) {
        public static final ModelPricingSchedule CLAUDE_3_5_SONNET = new ModelPricingSchedule(
                "claude-3-5-sonnet-20241022",
                new BigDecimal("3.00"),
                new BigDecimal("0.30"),  // 1 折 Cache Read
                new BigDecimal("15.00")
        );

        public static final ModelPricingSchedule GPT_4O = new ModelPricingSchedule(
                "gpt-4o-2024-08-06",
                new BigDecimal("2.50"),
                new BigDecimal("1.25"),  // 5 折 Cache Read
                new BigDecimal("10.00")
        );
    }

    public record ExecutionTokenUsage(
            int rawInputTokens,
            int cachedInputTokens,
            int outputTokens,
            int imageTileCount
    ) {}

    /**
     * 计算单次模型调用的绝对财务成本 (精确到 6 位小数)
     */
    public static BigDecimal computeExecutionCost(ModelPricingSchedule schedule, ExecutionTokenUsage usage) {
        Objects.requireNonNull(schedule, "schedule must not be null");
        Objects.requireNonNull(usage, "usage must not be null");

        // 1. 未命中缓存的常规输入成本
        BigDecimal uncachedTokens = BigDecimal.valueOf(Math.max(0, usage.rawInputTokens() - usage.cachedInputTokens()));
        BigDecimal inputCost = uncachedTokens
                .multiply(schedule.pricePerMillionInputUsd())
                .divide(ONE_MILLION, 6, RoundingMode.HALF_UP);

        // 2. 命中缓存的输入成本 (享受 1 折 ~ 2.5 折)
        BigDecimal cachedCost = BigDecimal.valueOf(usage.cachedInputTokens())
                .multiply(schedule.pricePerMillionCachedInputUsd())
                .divide(ONE_MILLION, 6, RoundingMode.HALF_UP);

        // 3. 输出成本 (高昂自回归解码，溢价 3~4 倍)
        BigDecimal outputCost = BigDecimal.valueOf(usage.outputTokens())
                .multiply(schedule.pricePerMillionOutputUsd())
                .divide(ONE_MILLION, 6, RoundingMode.HALF_UP);

        return inputCost.add(cachedCost).add(outputCost);
    }
}
```

> 3. **多模态降维压缩**：在 Hook 2 引入图像预切片与轻量抽取器，将 50 页报关单压缩为 150 字节 JSON，单工单直接压降 46.6% 的财务成本，百万工单节省超 4 万美元纯利。”
