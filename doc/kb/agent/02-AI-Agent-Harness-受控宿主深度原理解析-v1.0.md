## 一、 概念基石：重新定义 Harness

### 1.1 什么是 Harness？
> **核心定义**：  
> **Harness（受控宿主 / 挽具）是把“不可控的大模型执行图”与“高可靠的企业业务系统”隔开的受控沙箱、分布式事务外壳与安全隔离带。**

* **形象比喻**：
  * **LLM + LangGraph** 是一匹跑得飞快但经常抽疯的**烈马**（负责思考与图路由）；
  * **Harness** 则是套在马身上的**缰绳、马鞍、护具与围栏**（负责权限校验、踩刹车、限速、防止跳出赛道）；
  * 没有 Harness 的 Agent，本质上是把生产环境的数据库和 API 裸扔给一个概率论生成器。

### 1.2 图执行引擎（Orchestration Engine）与 Harness（宿主）的权责对齐

| 维度 | 图执行引擎 (如 LangGraph / CrewAI) | 受控宿主 (Harness) |
|---|---|---|
| **核心职责** | 状态节点拓扑跳转、条件分支、提示词装配 | 分布式事务持久化、安全闸门、租约并发控制、预算预占 |
| **对模型的假设** | 假设模型输出可信，可直接映射到函数调用 | **假设模型绝对不可信**，模型输出仅为“候选提案” |
| **崩溃处理** | 内存状态丢失，依赖简单内存重试 | 基于数据库 Checkpoint 自动恢复，分布式幂等防重 |
| **权限裁决** | 只要 Prompt 允许，模型可调所有工具 | 物理代码门禁，只有宿主能签发 `AuthorizedToolCall` |

## 二、 为什么生产环境必须依赖 Harness（5 大核心痛点）

```
                        大模型生成的不稳定指令 (Unreliable Commands)
                                          │
                                          ▼
             ┌─────────────────────────────────────────────────────────┐
             │                Harness Enterprise Guard                 │
             │                                                         │
             │   1. 提权攻击拦截  ───> [ 宿主签发 AuthorizedToolCall ]   │
             │   2. 并发脑裂防护  ───> [ 单调递增 Fencing Token + CAS]  │
             │   3. 超时未知悬挂  ───> [ operation_ref 异步对账机 ]     │
             │   4. 算力失控熔断  ───> [ Token 原子预算预占 BudgetPort] │
             │   5. 合规追溯断言  ───> [ 不可篡改 Run Receipt 收据 ]     │
             └─────────────────────────────────────────────────────────┘
                                          │
                                          ▼
                      企业级核心数据库与关键业务 API (Safe & Sound)
```

1. **防提权与越权攻击 (Prompt Injection)**：防止用户通过提示词欺骗模型生成管理员指令；
2. **防分布式脑裂与并发覆盖写**：防止多节点竞争同一会话导致的脏写与数据损坏；
3. **消除外部工具调用的副作用悬挂**：防止网络抖动超时后盲目重试导致的重复扣款或重复发文；
4. **算力预算原子控制**：防止递归死循环或恶意消耗导致企业账单瞬间爆仓；
5. **合规审计与不可抵赖性**：为所有高危操作生成法律级不可抵赖的执行收据（Receipt）。

## 三、 Harness 的 9 阶段不可绕过生命周期 Hook 深度剖析

Harness 通过驱动循环 `advance(run, fencing_token)` 提供 9 个不可穿透的拦截点：

```
   [Inbound Event]
          │
          ▼
   ┌───────────────┐
1. │  on_run_load  │ ── 校验租户身份、时效租约 (Lease) 与删除墓碑 (Tombstone)
   └───────────────┘
          │
          ▼
   ┌───────────────┐
2. │before_context │ ── 校验数据授权目的 (Purpose)，根据隐私策略脱敏和裁剪片段
   └───────────────┘
          │
          ▼
   ┌───────────────┐
3. │ before_model  │ ── Token 计数预测、出网合法性白名单校验、原子预占预算
   └───────────────┘
          │ (Model Call via Provider)
          ▼
   ┌───────────────┐
4. │  after_model  │ ── Pydantic Schema 强校验，剥离非法提权字段，记录实际消耗
   └───────────────┘
          │
          ▼
   ┌───────────────┐
5. │ before_action │ ── 【安全核心闸门】仅由宿主构造 AuthorizedToolCall，阻断伪造凭证
   └───────────────┘
          │ (Tool Execution)
          ▼
   ┌───────────────┐
6. │ after_action  │ ── 持久化 operation_ref，哈希校验；处理网络未知超时 (标 unknown)
   └───────────────┘
          │
          ▼
   ┌───────────────┐
7. │before_chkpnt  │ ── 单调递增 fencing_token + 数据库 CAS 乐观锁持久化状态快照
   └───────────────┘
          │
          ▼
   ┌───────────────┐
8. │before_finalize│ ── 聚合已完成目标与未完成项，生成只读 Run Receipt 聚合收据
   └───────────────┘
          │
          ▼
   ┌───────────────┐
9. │after_finalize │ ── Outbox 模式异步发布终态事件与不可篡改审计日志
   └───────────────┘
```

## 四、 分布式可靠性：Fencing Token 与 CAS 锁原理

在分布式集群中，当 Worker-A 发生长时间 GC 或网络假死，控制中心会将任务重新分派给 Worker-B。若 Worker-A 突然苏醒并尝试写回数据库，就会造成严重的**脑裂（Split-Brain）与状态损坏**。

Harness 通过 **单调递增的 `fencing_token` 与 CAS（Compare-And-Swap）** 解决此问题：

```
Worker-A (假死)                  数据库 (Postgres Checkpoint)                 Worker-B (接管)
   │                                   │                                         │
   ├─ 读取状态 (Token=10)                │                                         │
   │  [发生长时间 GC 假死...]             │                                         │
   │                                   │                                         │
   │                                   ├──────────────── 获取租约 (Token=11) ────┤
   │                                   │                                         ├─ 推进并成功提交 (Token=11)
   │                                   │<─── UPDATE checkpoint SET token=11 ─────┤
   │                                   │     WHERE token=10 (CAS 成功)            │
   │                                   │                                         │
   │                                   │                                         │
   ├─ Worker-A 复活尝试写入 (Token=10)    │                                         │
   │  UPDATE checkpoint ...            │                                         │
   │  WHERE token=10                   │                                         │
   │──────────────────────────────────>│                                         │
   │                                   │ (CAS 匹配失败! 当前 token=11)            │
   │<──────────────────────────────────│                                         │
   │  [抛出 CASConflictError 强行自毁]  │                                         │
```

## 五、 双进程架构与物理密钥隔离模型

为了彻底杜绝外部恶意提示词注入（Prompt Injection）导致 API Key 被窃取，Harness 脚手架采用**物理双进程模型**：

```
┌──────────────────────────────────────┐          ┌──────────────────────────────────────┐
│  Worker 进程 (cogniva-learning-agent) │          │ Provider 进程 (cogniva-model-provider)│
├──────────────────────────────────────┤          ├──────────────────────────────────────┤
│ - 运行 LangGraph 状态图与业务 Agent   │          │ - 独立容器/虚拟机部署，专职管理 API Key│
│ - 零 API Key，环境变量中无任何密钥   │   HTTP   │ - 负责 Token 预占、出网审计与速率限制 │
│ - 只有内部 RPC/HTTP 访问权限         │ ───────> │ - 统一接入外部供应商 (OpenAI/Qwen)    │
│ - 即使发生任意代码执行，也无凭证可偷 │          │ - 本地支持 100% 确定性的 FakeProvider │
└──────────────────────────────────────┘          └──────────────────────────────────────┘
```

## 六、 非幂等副作用与未知超时对账状态机

当 Agent 调用转账、发邮件、创建工单等具有**写副作用**的外部工具时，若遭遇网络超时（HTTP 504 / Connection Reset），直接重试可能导致二次执行。

Harness 的状态转移规约：

```
           [生成不可变 operation_ref]
                      │
                      ▼
             [before_action 门禁通过]
                      │
                      ▼
               (发起外部调用)
                      │
         ┌────────────┴────────────┐
         ▼ 明确成功                ▼ 网络抖动 / 读超时 (Read Timeout)
   [状态: success]           [状态标记为: unknown] (严禁原地盲目重试!)
         │                         │
         │                         ▼
         │                 [任务挂起进入 Reconciler 对账流]
         │                         │
         │                         ▼ (使用 operation_ref 发起带退避的反查)
         │           ┌─────────────┴─────────────┐
         │           ▼ 对端已记录成功             ▼ 对端查无此操作
         │      [补录为 success]             [确认安全，触发单次重试]
         ▼           │                           │
  [落地业务 Checkpoint 与收据] <───────────────────┘
```
